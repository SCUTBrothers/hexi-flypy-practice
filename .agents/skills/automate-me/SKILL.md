# 提炼个人工作模式（automate-me）

一套引导式流程，用于将用户日常的工作习惯、路由偏好与工程约定提炼成供智能体遵循的专属 `-mode` 技能（如 `cobe-mode` 或 `<handle>-mode`）。

本技能负责串联调度三个环节：内置的历史会话挖掘与结构化问答（步骤 1–3）、技能编写规范指导（步骤 4：优先查找并使用环境中与 `skill-creator` 语义相近的技能创建指导技能，正文同时遵循 `writing-for-agents` 的执行说明规范），以及 `technical-writing` 与 `unslop`（步骤 5 文风打磨）。本技能只负责编排先后顺序与个人 `-mode` 技能的专属约束。

## 执行流程

### 0. 检查是否已有现成模式技能

在当前仓库技能目录（如 `src/skills/**/*-mode/SKILL.md`、`skills/**/*-mode/SKILL.md`、`.agents/skills/**/*-mode/SKILL.md`）及全局个人技能目录（如 `~/.agents/skills/*-mode/SKILL.md`）中查找与用户标识匹配的 `-mode` 技能。若已存在且用户未在消息中指明意图，先向用户确认：

- **更新现有技能**（多次运行时的默认选项）
- **推倒重写**（极少使用；动手前先问清原因）

若选择更新模式，后续流程作如下调整：

- 步骤 1 仅挖掘该技能上次修改之后的历史会话（`git log -1 --format=%cI <path>`）。
- 步骤 2 询问近期有哪些变化或遗漏，而非从零开始收集。
- 步骤 4 直接就地编辑现有文件：保留用户未推翻的章节，根据新证据修订已有规则，仅在出现全新规则时才新增章节。

### 1. 挖掘用户的历史会话

在并行分发子智能体之前，按 `recall` 技能中对应宿主的参考指南（`pi` / `codex`）定位当前活动工作区的本地会话记录路径。**只准读取当前授权工作区下的会话记录，严禁使用通配符跨工作区目录扫描无关项目的私人聊天，并在记录任何证据前剔除凭据与私密信息。**

在该范围内普查近期的智能体对话，寻找反复出现的行为模式。将历史会话按时间段切片（例如把过去 2–4 周切分为 3 个时间切片，保证每个切片都有充足素材），并行派生子智能体分别挖掘。每个切片挖掘子智能体只读取父智能体传入的工作区会话路径，搜寻以下信号，并返回一份带证据指针的简短结构化模式清单：

- 回复偏好（篇幅长短、语气风格、排版格式、“说人话/精简点”之类的纠正）
- 委派与路由习惯（何时启用子智能体、偏好的技能串联顺序、并行度）
- 验证标准（什么才算“完成”、单元测试还是真实运行复现、证据展示方式）
- 代码与文风纪律（编码风格、常引用的原则、lint 与格式化工具链）
- 研发流程约定（Git 工作树、提交粒度、何时允许提交或推送）
- 元级偏好（任务中途顺手修技能、采用前如何核对证据）

在将某条信号采纳为规则之前，必须先跨时间切片交叉核对：**在 2 个及以上切片中反复出现的模式才具备高置信度**；只出现过一次的孤立信号通常属于偶然噪声，应予舍弃。

### 2. 结构化向用户提问

仅靠挖掘历史会话，抓不到用户尚未在过往对话中表露过的意图。优先调用宿主提供的结构化多选提问工具（若宿主无该工具，则在消息中给出清晰的编号选项列表），不要让用户对着空白输入框从头手打。

提问结构：每次问 1–2 个问题，每个问题提供 4–6 个选项；分类摸底题支持多选。先从宽泛的领域切入（如“哪些维度最需要写进你的模式技能？”），再针对用户选中的领域追问具体规则。结构化问答结束后，最后补一个开放式提问，兜底收集选项未能覆盖的细节。

切勿一股脑甩出 20 个问题。

### 3. 归类整理发现项

将挖掘出的高置信度历史信号与用户回答汇总后按章节归类。常见章节如下（只保留确有个性化规则的项）：

- **技能路由（Routing）**：不同场景优先分发到哪些专项技能或串联路径。
- **回复风格（Response style）**：篇幅、语气、排版格式。
- **自主边界（Autonomy）**：哪些可逆操作直接推进，哪些外部或不可逆操作必须停下确认。
- **子智能体（Subagents）**：并发隔离策略与父会话复核职责。
- **文风与代码纪律（Prose / code discipline）**：遵循的底层原则、格式化与 lint 工具链。
- **审阅与验证（Review and verify）**：复现要求、验收技能与真实运行证据。
- **技能维护（Skills）**：采用前核对证据、结构化约束优先。

可参考 `cobe-mode` 的骨架与颗粒度，但每条规则都必须反映用户本人的真实偏好，切勿填充空泛套话。

### 4. 起草或修订技能文件

优先在当前可用技能中查找并读取关于「创建/编写技能」的指导文档（例如 `skill-creator` 或语义相近的技能），并结合 `writing-for-agents` 确定触发条件、完成标准与参考文件位置；若环境未提供外部编写指南，则直接以 `writing-for-agents` 为准，并叠加以下个人模式技能专属约定：

- **路径**：更新已有模式技能时沿用原路径；新建时按用户意图放入当前技能库（在 cstack 内将已确认采用的技能写入 `src/skills/<category>/<handle>-mode/SKILL.md`）或 `.agents/skills/<handle>-mode/SKILL.md`。
- **标识（Handle）**：用户自选的简短标识符（如 `cobe`）。
- **Frontmatter `description`**：保持为单标量 YAML 字符串（含特殊标点时加引号），触发范围聚焦在模式名称、入口定位与“按个人风格工作/路由”，切勿写成“写代码”或“审阅 PR”这类宽泛通用词。
- **默认设置 `disable-model-invocation: true`**：仅当用户明确要求每轮对话自动加载时才移除该标记。

### 5. 打磨文风与措辞

沿用步骤 4 的完成标准，结合 `technical-writing`、`unslop` 打磨每一行指令，大刀阔斧砍掉废话。模式技能是直接改变行动的精准指令，不是长篇说明书。将初稿展示给用户审阅并迭代收敛。

### 6. 落地交付

按目标仓库规范完成格式化与链接核验；未经用户明确要求，不擅自执行 Git 提交、推送或创建 PR。

## 护栏约束

- **切勿对单次对话过拟合。** 只在某次聊天里随口提过一次、甚至在别处自相矛盾的偏好只是噪声；必须有多次重复实例或用户明确确认才能写入技能。
- **切勿堆砌空泛修辞。** 把其他技能的正文复述一遍、生造隐喻或写“沟通要清晰”这类正确的废话，纯属徒增上下文开销。“段落要短；对比方案用表格；未经要求绝不自动 commit”才配写进去。
- **用双链引用代替内容内联。** 用户日常依赖的其他技能与 `principle-*` 原则一律以双链路径引用，不要把目标技能的正文复制粘贴进来。
- **不要为了结构工整而硬凑章节。** 某个维度没有特殊规矩就直接略掉整节。
- **正文中统一使用通用称谓。** 在指令中统一写“用户”，不要混写作者名字。

## 效果评估

`-mode` 技能属于高度主观的个性化产出，通用技能创建流程中的自动化基准评测跑分循环在此并不适用。直接请用户本人核对体感（vibe-check）：读起来是否符合其真实行事风格、有无遗漏关键习惯，确认无误即可交付。仅当该技能在后续使用中出现触发失准时，才按需优化 `description`。

## 何时不应使用本技能

- 只想编写一个针对特定任务的普通新技能（而非个人全局 `-mode` 技能）：直接使用环境中的技能创建指导技能（如 `skill-creator`）或按 Agent Skills 规范编写即可，无需挖掘历史会话。
- 只想从当前单次会话提炼一条具体经验沉淀到某个已有专项技能：直接用 `reflect`。
- 只想根治仓库里反复出现的某类具体 Agent 错误：直接用 `correct`。
