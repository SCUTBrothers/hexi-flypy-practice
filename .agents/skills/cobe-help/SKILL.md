# 技能栈选型与使用向导（cobe-help）

解答关于当前技能栈的选型、区别与用法疑问，提供可直接复制发送的提示词示例，并附上目标技能文件链接。**回答帮助类问题时严禁直接动手改代码或执行业务任务**：用户只是在确认该用哪个技能，应把提示词交给用户自己决定是否发送。

如果用户的消息并非询问用法，而是直接下达具体工程任务（例如“用技能栈帮我排查这个报错”），则不属于帮助咨询：请直接读取 `cobe-mode` 并按其路由规范执行任务。

本文档将常见场景映射到对应的技能文件；**向用户推荐任何技能前，必须先读取目标技能真实的 `SKILL.md`**（若当前技能目录下新增了下方未列出的技能，一并读取其 YAML frontmatter），一切细节以目标技能文件为准。

## 判断用户诉求

根据用户消息与当前对话上下文识别诉求；若诉求明确（如“我想审查 PR 但怕全是废话建议，该用哪个？”），直接给出解答。若诉求过于宽泛，先提供以下方向供用户选择：

- 按当前场景推荐最合适的技能
- 辨析几个容易混淆的技能
- 了解如何用 `cobe-mode` 自动路由或组织高质量提示词
- 了解子智能体要求（`require_subagent`）与手动触发机制
- 沉淀经验或定制个人习惯

回答涉及“如何证明应用改动真正有效”的问题时，顺带检查当前业务仓库是否已有 `.agents/skills/verify-*` 验证技能；若尚无，可提示用户先用 `create-verification-skill` 生成项目验证脚手架。

## 一键自动路由 vs 手动点名技能

- **不记得具体技能名，或任务需要多步配合**：直接使用 `cobe-mode`，只需在消息中写清“目标 + 可客观判定的完成标准”（写法见 [references/prompting.md](./references/prompting.md)），它会根据请求自动匹配并加载最合适的专项技能。
- **只想精准执行某一个独立环节**（更轻量，或只想运行特定一步）：对照下方列表直接调用对应专项技能。

## 按场景选择技能

标有 `[需子代理]` 的技能在 frontmatter 中声明了 `meta.require_subagent: true`：在支持子智能体的宿主中会自动隔离上下文或并发执行；在未配置子智能体的单会话宿主中虽可降级运行，但优先推荐单会话原生技能。

- 不确定该调哪个技能，希望把任务交给路由器自动匹配并串联执行：`cobe-mode`（子代理需求按命中的下游技能而定）
- 动手写代码前，先确认智能体是否真正读懂了目标与核心问题：`in-your-own-words`
- 心里有画面但缺乏行业词汇说不清需求，先学专业术语与跨界先例再重写描述（只重写，不执行）：`reframe`
- 设计决策相互依赖，需要和用户分轮厘清取舍后再定方案：`grill-me` `[需子代理]`
- 发送复杂提示词前先深化打磨（补充专家视角与验证手段，只返回新提示词）：`sharpen`
- 把上一条充满术语的复杂回复用通俗大白话重说一遍：`bro`
- 摸清现有子系统如何运作，或确定新代码应该放在哪里：`how` `[需子代理]`
- 查明某段代码为何演变成当前结构，或某个历史设计的来龙去脉：`why`
- 融合运行机制与历史背景，用平实语言与递进图示由浅入深讲透系统：`teach` `[需子代理]`
- 新开窗口或恢复工作前，跨近期多次会话与实时 Git/PR 状态找回进展：`recall` `[需子代理]`
- 在当前长会话中途快速同步自上一条消息以来的进展，并列出待拍板事项：`ketchup`
- 切换窗口或移交任务前，为下一会话写一份包含证据指针与下一步的交接单：`handoff`
- 判断已有模块是否值得重构，对比维持现状、等价复用与模块深度的取舍：`architecture-review`
- 编写或重构跨函数/模块边界的代码前，先敲定数据形态并权衡结构方案：`architect`（大方案转 `arena` 时 `[需子代理]`）
- 访谈与代码核查已拍板，将行为契约、技术决策与不碰范围冻结为 `spec.md`（不重新发问）：`to-spec`
- 将已定稿的 `spec.md` 拆解为顺序可独立验证的垂直切片任务单（`tickets/`）：`to-tickets`
- 在干净上下文中接手单个垂直切片任务单，按边界实现、实跑验收并回写状态与 commit：`run-ticket`
- 状态规则或界面布局存在分歧，需要用可交互的一次性原型实测定夺：`prototype`
- 针对同一复杂任务并行探索多套方案，盲审选出底座并嫁接其余方案亮点：`arena` `[需子代理]`
- 读写 `.ts` / `.tsx` 代码时遵循严格类型建模与系统边界解析（自动按需生效）：`typescript-best-practices`
- 只有故障现象、复现不稳或根因不明，需要先建立可重复的故障信号再定位根因：`diagnosing-bugs`
- 存在低成本本地测试路径时，用“失败测试先行”方式修缺陷或加功能：`tdd`
- 对照最终确认的需求评审当前改动、提交或 PR，核查遗漏、越界实现与调用方回归：`code-review`
- 提交评审前交由独立视角剔除冗余注释、抑制标记并理顺局部结构：`no-comments` `[需子代理]`
- 派独立红队对手实弹运行并设法攻破当前改动或设计，只保留实锤真缺陷：`interrogate` `[需子代理]`
- 评估一段 diff 在改动范围外会波及破坏哪里，并跑代码证实核心安全事实：`blast-radius`
- 对多个子目录/分片并行执行核查，或按客观硬判据多路竞速汇总成一张总表：`swarm` `[需子代理]`
- 运行基准测试或汇报性能数据前，核验瓶颈、配置调优与算术上限（自动按需生效）：`benchmark-checklist`
- 为缺少自动化端到端验收手段的项目生成本地 `verify-<app>` 技能与功能地图：`create-verification-skill`
- 在应用代码演进后巡检并同步项目的 `verify-<app>` 验证技能与功能地图：`maintain-verification-skill` `[需子代理]`
- 面对无现成流程的大型迁移、跨模块改造或异步长任务，量身设计可审计工作流：`figure-it-out` `[需子代理]`
- 通过本机 CLI 调度异构外部模型分担重逻辑实现、疑难排障或对抗式第二意见审查（自动按需生效）：`dispatch`
- 在长时或多阶段运行期间用仅追加 TSV 日志记录决策轨迹，并在交接前审阅：`show-me-your-work` `[需子代理]`
- 依据当前 diff 与实测结果起草供审阅者阅读的 PR 正文：`pr`
- 撰写或审阅技术文档、RFC、README 与提交信息（中文为主兼容英文）：`technical-writing`
- 消除中文文章或大段叙述中的 AI 写作套话、禁用词与机械结构：`unslop`
- 编写或修订供 Agent 执行的技能、AGENTS.md 及按需参考文档：`writing-for-agents`
- 从当前会话复盘提炼半年后仍成立且改变行动的经验，沉淀回技能文件：`reflect`
- 归纳仓库内反复出现的同类 Agent 错误，优先用架构/类型/Lint/测试根治：`correct`
- 从近期工作区会话与结构化问答中提炼个人习惯，生成或更新 `-mode` 技能：`automate-me` `[需子代理，需外部技能: skill-creator]`

## 高频易混技能辨析

- **`in-your-own-words` vs `reframe` vs `sharpen` vs `grill-me`**：`in-your-own-words` 复述已有目标、校准双方理解；`reframe` 解决叫不出行业术语的问题，先教专业词与跨界先例再用行话重写描述；`sharpen` 在不扩范围的前提下把提示词推深到一手材料与验真标准（常接在 `reframe` 之后）；`grill-me` 面向尚待敲定的设计分支，通过分轮提问逐项拍板取舍。
- **`how` vs `why` vs `teach`**：`how` 查代码现在怎么运转；`why` 翻 Git/PR 历史查当初为何这样写；`teach` 同时调动两者并用通俗语言配递进图把来龙去脉讲透。
- **`recall` vs `ketchup` vs `handoff`**：`recall` 在新会话跨近期多次聊天记录与 Git/PR 找回工作全貌；`ketchup` 在当前长会话中同步“自上一条消息以来的进展”与待拍板项；`handoff` 在离开旧会话前主动生成交接文件，交给下一会话直接接棒。
- **`code-review` vs `architecture-review` vs `architect`**：`code-review` 围绕本轮具体 diff 核查需求偏差、调用方回归与可验证精简；`architecture-review` 面向存量模块评估值不值得重构，无需 diff 即可使用；`architect` 在目标方向已明确后，负责细化接口、数据类型与模块边界。
- **`grill-me` vs `to-spec` vs `to-tickets` vs `run-ticket` vs `figure-it-out`**：`grill-me` 负责访谈拍板；`to-spec` 把已拍板的结论冻结为 `spec.md`；`to-tickets` 把 `spec.md` 拆成按顺序可独立验证的垂直切片任务单；`run-ticket` 在干净上下文中完成其中一片并回写状态与 commit；`figure-it-out` 面向无现成流程、需要自定义实验循环与多节点并行编排的大型非标迁移。
- **`diagnosing-bugs` vs `tdd`**：`diagnosing-bugs` 用于现象模糊或复现不稳时，从零建立故障信号、提出假设并定位根因；`tdd` 适用于预期行为与低成本测试入口已明确时，先写失败测试再做修复。
- **`arena` vs `swarm` vs `dispatch`**：`arena` 在同一宿主内并发做同题多解、盲审并手工嫁接亮点；`swarm` 在同一宿主内做分片盘点（partition）或客观指标赛马（race），汇总成一张 `PASS / ISSUES / BLOCKED` 表；`dispatch` 则是单会话通过外部 CLI 调度**异构模型**协同实现或给第二意见，主控负责起草规格、验收 diff 并对人转述。
- **`interrogate` vs `blast-radius`**：`interrogate` 攻的是本次改动自身的漏洞（派红队在隔离工作树里写复现把新逻辑跑挂，滤除一切没跑过的口头挑刺）；`blast-radius` 查的是向外波及面（diff 之外三跳开外的调用方、协议或时序会不会被连带震碎，并跑代码证明安全核心事实）。
- **`technical-writing` vs `pr` vs `writing-for-agents` vs `unslop`**：面向人类工程师写 README、RFC、API 参考或操作指南用 `technical-writing`；面向审阅者撰写含实测证据与合并风险的 PR 正文用 `pr`；面向执行指令的 Agent 编写技能或 `AGENTS.md` 用 `writing-for-agents`；专门清除中文文章与叙述中的 AI 套话用 `unslop`。
- **`reflect` vs `correct` vs `automate-me`**：`reflect` 在单次任务做完后把刚学到的经验补进某个专项技能；`correct` 针对业务仓库里反复踩的坑加 lint/类型/测试硬约束；`automate-me` 跨近期多次会话提炼你个人的全局习惯来更新 `-mode` 技能。

## 常见机制疑问排查

- **自然语言提问时，某项专项技能没有自动生效**：除 `typescript-best-practices`、`benchmark-checklist` 和 `dispatch` 支持按需自动匹配外，其余入口技能均设有 `disable-model-invocation: true` 以免日常误触发和挤占上下文。请显式点名调用（如 `pi` 中 `/skill:<name>`、`codex` 中 `$<name>`），或统一通过 `cobe-mode` 自动路由。
- **对话聊了很多轮后，`cobe-mode` 约束力下降，或新问题被当成旧任务继续做**：单次消息加载的技能会随上下文拉长而衰减；开启独立新任务时重新带上 `cobe-mode`，或在消息开头写明“新任务：……”。
- **当前宿主环境没有安装子智能体扩展或缺少外部依赖技能怎么办？**：未安装子智能体时，优先选用未标注 `[需子代理]` 的单会话技能（调用带 `[需子代理]` 的技能时模型也会在主会话降级完成）；声明了 `meta.require_skills` 的技能（如 `automate-me` 依赖 `skill-creator`）需确认宿主已内置（如 `codex` 自带）或提前安装对应外部技能。完整分类见仓库根目录 `catalog.md`。
- **智能体只跑过编译或单测就宣称“修好了”**：直接在回复中点名原则：“按 `principle-prove-it-works` 原则，给我看真实运行输出，不要只看构建通过。”更多一句话纠偏技巧见 [references/prompting.md](./references/prompting.md)。

## 回复格式

开门见山给出推荐的技能名称（说明核心理由、是否需要子代理支持；若需两步串联则写明先后顺序），在代码块中附上 **1 条可直接复制替换参数使用的提示词示例**（可参考并改编自 [references/recipes.md](./references/recipes.md)），并附上目标技能文件链接。除非用户要求看全景列表，否则保持精炼，只讲当前场景最该用的那一个（或一对）。
