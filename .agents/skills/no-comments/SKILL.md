# 清理代码注释（no-comments）

派生 Comment Sicko 子智能体审查注释，对确认成立的问题执行修复，尊重独立子智能体的新鲜视角。

## 范围

优先使用调用方指定的文件或 diff；未指定时，使用当前相对基准分支（默认 `main`）的 diff（包含工作树未提交改动）。

## 步骤

1. 派生一个独立子智能体，向其传入审查范围与 [references/comment-sicko.md](./references/comment-sicko.md) 简报。
2. 核查子智能体的报告与注释 diff。驳回任何擅改业务逻辑、越出指定范围、误删受保护例外、错报 `MUST KILL` 理由，或将有意保留的正常代码定罪的标记。针对“我们自己代码反直觉”的重构标记继续保留为待修项，不要恢复那些注释。保留项（keep）唯有证明确实受制于外部不可改因素时才准存活。补查范围内遗漏的局部 lint 与 TypeScript 抑制注释；涉及正确性或安全性的抑制仍作为可执行的 `MUST KILL`。仅在具备确切例外条款与范围内实证时才恢复被删注释。对依据单薄的 `IMPORTANT` 或 `do not remove` 在决定删留前，先追踪对应符号或对其运行 `why`：删除存疑时不恢复；保留理由被证伪或仍存疑时直接删掉。若整份报告被驳回，点明原因回滚重跑一次；第二次仍不合格则如实报告未决项并中止。
3. 对简单明确的待修标记直接动手消除（删死代码分支、去掉无用参数、改用真实 API）。若修复涉及结构调整，对认可的待修集及周边代码运行一次 `architect`，停在结构草图阶段；由步骤 4 落地实现。
4. 在限定范围内实施最小的根因修复，移除所有点名的临时绕行写法（workaround）；若根因超出当前范围，合入范围内最小修复并将其余部分列为未决项。`principle-fix-root-causes` 与 `principle-redesign-from-first-principles` 仅指导修复方向，不授权扩大文件围栏或顺手修范围外的同类实例。绝不在症状表面硬贴防御条件。
5. 对写着 `do not remove`、`do not change wording`、`修改前请联系 X` 等声称约束的注释：确属外部不可改因素的保留；其余向用户提议范围内成本最低的类型、运行时检查、测试或 CI lint 编码方案，等待交互确认。获批后先编码约束再删注释；未获批则删掉注释、将该约束列为未决项并简述范围外跟进方案。
6. 汇总报告：删除注释数、恢复注释数、重跑情况、架构草图、已落地的代码修复、约束编码提议与已落地编码、尚未强制执行的约束及其他未决事项。
