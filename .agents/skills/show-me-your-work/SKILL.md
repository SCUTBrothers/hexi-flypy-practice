# 展示工作轨迹（show-me-your-work）

只维护一份唯一权威日志。

## 格式

使用单个 TSV 文件，每项决策占一行。单元格内容保持单行。证据列只写位置指针，不写大段文字说明。

复制 [references/decision-log-template.tsv](./references/decision-log-template.tsv)（表头行）开启一份干净的新日志。各列含义如下：

- **ts。** ISO8601 时间戳。
- **phase。** 所属阶段或工作流分支。
- **decision。** 选定了什么或做了什么，浓缩为一行。
- **why。** 用通俗语言说明原因。如果是由某项原则驱动，直接用平实的话讲清楚，不要只贴一个行话标签。
- **evidence。** 能证明该项的链接或路径：提交 SHA、PR 编号、`file:line`，或产物、性能剖析记录（trace）、截图的路径。绝不要写成段落。
- **result。** 最终结果或断言状态：`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

下面是一个平实易懂的示例，方便审阅者一眼扫完：

```text
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先盘点工作量，约 100 个组件、耗时约 75 小时	启动长任务前先摸清总体规模	commit 3a9f1c2	发现开工前需先理清的 5 个问题
2026-05-24T09:40:00Z	harness	动手改动前先对旧版本截图	便于新旧对比，捕捉任何视觉变化	scripts/snapshot.sh, baseline/	已保存 120 张基准参考截图
2026-05-24T11:15:00Z	widget	迁移组件样式，保持外观完全不变	控制改动粒度，确保视觉效果一致	commit 7c21e0a, pixel-diff 0	外观完全一致，测试通过
2026-05-24T12:30:00Z	widget	子智能体产出的截图为空白，废弃其改动	直接检查真实产物文件，不轻信文字摘要	worktree reset	已回退，并收紧下次调用的任务指令
```

## 记录一行

写每条记录时，就像当面跟队友交代你刚干了什么一样：用平实词汇、写具体动作，不搞 AI 套话或抽象行话（`unslop` 技能同样适用于日志文本）。

使用辅助脚本 [scripts/log.sh](./scripts/log.sh)（调用格式：`scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`）写入。它会自动打上 `ts` 时间戳，首次调用时写入表头，剥离多余的制表符与换行符，并在以 `=`、`+`、`-` 或 `@` 开头的单元格前加单引号。直接用 `printf` 追加一行也可以，但若单元格内容来自生成文本或用户输入，同样需要留心这些特殊首字符。

只记录关键决策点与检查点，不要流水账式地记录每个动作：选定了某条分叉路径、完成了某个工作单元及其验证结果、因某触发条件而转向或回退、暴露出阻塞问题、修好了某道准入检查。循环运行（loop runs）每轮迭代记一行。显而易见的琐事一律略过。

一次“运行（run）”指单次智能体会话，包括其后续轮次及会话摘要。接续会话、更换智能体或新开聊天窗口都算开启了一次新运行。当一次运行向已有记录的日志追加内容时，它的第一行必须将 `phase` 设为 `start`；若中间穿插了其他运行写入的 `start` 行，本运行随后再次追加的第一行也必须将 `phase` 设为 `start`。因此，同一运行在后续轮次重新回来写日志时，必须先读取日志末尾几行，确认期间是否有其他运行写入过。`start` 行用于标明它上方哪段 `ts` 范围内的记录不是由本次运行写入的，其 `evidence` 列则标明本次运行的身份（如智能体 ID）。切勿将 `phase` 的 `start` 值挪作他用。

## 存放位置

日志默认作为本地工作产物保留，不提交进版本库。存放在工作目录的 `decisions.tsv` 下；若同时推进多项任务，则存放在 `.audit/<task-slug>.tsv`，并排除在 Git 提交之外。

只有当任务规模足够庞大、审阅者必须查看决策轨迹才能信任最终结果时，才将日志提交入库。

## 规则

- **仅追加（Append-only）。** 发现之前的决策有误时，新增一行予以覆盖更正，绝不修改或删除历史行。
- **优先使用已提交脚本生成的证据**，而非手工临时拼凑的一次性产物（遵循 `principle-encode-lessons-in-structure` 原则技能）。

## 对照会话记录审计日志

在运行结束、向用户交接之前，核验日志是否如实反映了过程。按 `recall` 技能中对应宿主的会话路径指南（`pi` / `codex`）读取当前活动工作区下本次运行的会话记录；严禁使用通配符跨工作区目录搜索，以免越界读取无关项目的私人聊天。将本次运行写入的各个日志片段逐行与实际发生的情况比对（每个片段从本次运行的某条 `start` 行开始，若日志由本次运行新建则从首行开始，直至另一运行写入的下一条 `start` 行结束）：

- 核对每一行是否都对应真实的决策或动作。
- 核对每一行的证据路径或链接是否真实可达，且确实能证明该行所声称的结论。
- 凡是左右了工作走向的分叉选择、方向调整或中途放弃的方案，若未记录在案均属遗漏，必须补齐。

修正日志记录，而不是篡改历史故事。审计绝不编辑或删除已有行，哪怕某行是凭空编造的。如果某行既不对应真实决策也不对应真实动作，或者其结论、证据有误，请追加新行覆盖旧行：如实写明实际情况，并附上真实可达的证据指针。本次审计不检查本次运行日志片段之外的其他行；但如果本次运行的工作证实了此前某行有误，同样像处理错误决策一样追加新行予以覆盖更正。

## 跨模型审阅决策轨迹

在交接给用户前，派生一个独立审阅子智能体（宿主支持多模型配置时，优先选用不同于执行本次任务的另一家模型厂商）——自审不能替代独立审阅。该子智能体负责通读审计轨迹日志与本次运行的会话记录，标出需要用户留意的风险点：不是把活重干一遍，而是扫描哪些地方不够理想或暗藏风险：

- 已记录但证据薄弱或缺失的决策。
- 被跳过的验证步骤，或声称已验证但会话记录中毫无凭证的步骤。
- 事后回看存在风险的选择（过早拍板、范围蔓延、只掩盖表面症状）。
- 用户粗略浏览时容易漏掉的盲区。

凡是产出了决策轨迹的运行，交接回复末尾都必须附带一个 `Attention`（关注事项）小节。第一行单独写明审阅模型（`reviewed by <model>`），随后逐条列出风险项并指向具体的日志行或会话时刻。如果没有发现问题，写 `No flags` 是合法结论，但只写模型名称不写结论则不行。

## 审阅轨迹

从上往下通读，顺着证据指针抽查核实。提交入库的 TSV 文件在 GitHub 上会自动渲染成表格；在终端里可执行 `column -s$'\t' -t decisions.tsv` 对齐查看。

## 与其他技能组合

其他技能需要记录审计轨迹时，应直接复用本技能，不要另起炉灶自造格式。直接按名称引用本技能并交由本技能定义格式，无需在其他技能中重复抄写各列定义。
