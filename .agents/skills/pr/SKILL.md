# 撰写可审阅的 PR 正文（pr）

先核对当前分支相对目标分支的实际 diff 与已执行的验证，行文沿用项目既有的领域术语。若仓库自带 PR 模板，保留其必填栏目，将以下内容填入对应位置。默认仅交付正文草稿；创建或更新远端 PR 须先获得用户授权。

## 摘要

讲清用户或调用方能直观感知到的行为变化，按改动特点选用最直观的最小视图，并紧贴对应的简短说明摆放：

- 算法与核心逻辑用伪代码，调用链路用调用树，界面布局用组件树，文件职责用浅层目录树，跨组件交互用时序图，局部行为变化用精简 diff。
- 若改动以新增为主、删节会掩盖归属或顺序，或审阅者需要一段可直接参考的接口，则展示完整的相关代码块；简单改动用一句话交代即可。

文字表达按 `technical-writing` 保持紧凑直白。视图选型思路见 [来源与致谢](./CREDITS.md)。

## 验证依据

按 `principle-prove-it-works` 引用真实运行结果：

- 视觉改动优先附上同一场景的前后对比截图；逻辑改动列出能区分改前与改后行为的具体输入和断言。
- 若存在安全、低成本的本地验证命令且允许执行，在相同条件下分别于基准版本和当前版本运行，并引用各自实测输出。
- 若仅能实测一侧，或用户限定只能引用现有证据，须明确标明哪一侧来自实测、哪一侧由 diff 推断得出。

## 合并风险

先给出回滚难易度判断（易于回退还是不可逆改动）和一句话影响范围，再列出具体受影响的调用方、数据或用户。若单纯回退代码无法消除已迁移的数据或已对外发出的副作用，须写明彻底恢复还需执行的步骤。涉及跨模块连带影响时，先用 `blast-radius` 核实，再将确认后的结论写入正文。
