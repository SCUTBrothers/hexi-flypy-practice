# 依赖与测试边界

围绕同一个可观察结果辨别所涉依赖的类型，再权衡接缝位置、替换手段与验证成本。

| 依赖类型           | 评审核对要点                                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 进程内计算或状态   | 合并过浅的模块后，能否直接通过公开入口验证结果？纯计算通常不需要额外引入适配器。                                                         |
| 可在本地替代的依赖 | 优先沿用能验证目标行为的本地数据库或文件系统替身；替换点可留在模块内部，但须核对替身在错误、排序、事务等关键语义上是否逼真。             |
| 自有远程服务       | 若核心逻辑同时需要生产传输层和受控测试实现，评估把传输层收在端口后的收益，写明生产实现与内存替身各自承担什么、哪些网络契约仍需独立验证。 |
| 不可控的第三方服务 | 将第三方交互收拢到窄接缝处，在接缝上模拟已知响应与异常，再从业务入口验证整体行为；第三方服务自身的实际表现另行核实。                     |

拿一条真实调用试用候选接口：调用方能否直接传入自己手头已有的依赖？纯计算能否直接返回值而非修改外部状态？走完一次调用需要几个方法、多少参数与初始化步骤？据此衡量各方案究竟藏住了多少复杂度，以及必要的写入副作用由谁承担。

提议迁移或合并测试时，先将原有断言逐条映射到新接口的可观察行为（含独有的错误分支与副作用）。只有确认替代测试已切实覆盖原有断言后，才建议淘汰与被删内部结构强绑定的重复单测；仍能捕获独立回归风险的断言必须保留。
