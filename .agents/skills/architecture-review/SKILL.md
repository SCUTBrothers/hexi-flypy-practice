# 评审现有架构（architecture-review）

以只读方式审视现有代码结构，在当前会话中给出有证据支撑的取舍与建议。

## 1. 定位维护吃力的真实痛点

从用户指出的模块、反复牵连修改的业务规则或难以测试的入口切入；若用户只给了整个仓库，可借助近期提交的变更热点缩小范围，热点分散时再逐步展开。

沿一条代表性调用链路从入口走到最终结果，逐项列出调用方被迫了解的不变量、调用顺序、配置、报错语义、性能约束与副作用。重点关注三类信号：一个业务概念要跨多少个文件才能看全、公开接口泄漏了哪些内部细节，以及测试只盯着小函数却漏掉了它们组合后的真实故障。沿用项目既有的业务术语，把每处痛点落到具体文件、调用点或测试上。结合既有契约判断调整是否可行；若建议改动既有约定，须写明眼下的真实迁移代价。缺乏历史动机证据时，直接按今天的使用场景做评估。

## 2. 用真实调用检验候选方向

- **简洁度与模块深度**：试着做「删除检验」——设想直接抽掉这一层。若只是省去一次机械转发，可考虑内联消除；若多个调用方原本都要各自重复处理同一组复杂规则，说明这个深模块正用简洁的接口替调用方兜住了复杂度，值得保留。衡量模块深度时，看调用方要学多少知识才能把事办成、同一条业务规则要改几处，以及能否直接通过公开接口验证行为。
- **等价复用**：在两处相似代码处各找一个真实调用方，核对它们执行的是否真是同一条业务规则、未来是否必然同步演进。逐项比对默认值、失败语义与副作用，据此给出可复用的现成实现，或说明为何应当保留各自独立。
- **接缝与适配器**：接缝是允许替换行为的边界位置。提议引入新端口（port）时，必须举出至少两个有实际价值的适配器（例如生产实现与能够模拟失败场景的测试替身）；只有一个实现的现有模块同样可以封装复杂规则，无需硬拆接口。优先通过调用方使用的公开入口验证可观察行为，仅服务于测试的内部替换点可留在模块内部。涉及 I/O、端口抽象或测试合并时，对照 [依赖与测试边界](./references/dependencies-and-tests.md) 核验方案。

## 3. 同场景比较并给出建议

围绕同一个真实调用场景，将「维持现状」与可行的重构方案放在一起对比。可分别从最常见调用、最小接口面或真实替换需求出发，构造出职责归属或接缝位置确有差异的候选方案；必要时各给出一行调用示例，点明由谁负责调用顺序、错误处理与资源释放，以及哪些细节得以藏进模块内部。

逐项比较各方案的改动集中度、兼容与迁移成本，以及如何验证既有行为不被破坏。多个候选并存时明确给出首选与理由，并将仍需补证的设想单独标出；若重构收益不足以覆盖成本，直接建议维持现状。建议中须引用关键文件与调用方；一旦方向敲定、用户需要细化具体接口与实施设计时，可衔接 `architect`。
