# 维护项目验证技能（maintain-verification-skill）

应用一旦变更，功能地图就会过时失真。本技能是 `create-verification-skill` 所生成技能（或任何带有功能地图的项目本地验证技能）的日常维护闭环。严格核验的粒度是“功能（feature）”，而非逐字逐句：既要从源码层面核对每个功能文件，也要在真实运行环境中实际操作每个功能，但无需将每个列表项都机械拆成独立的终端命令去跑。

## 巡检结论

从以下三项中选定一项，并明确告知结论：

- **`clean`（无变更）**：每个功能均已完成源码核对与真实运行覆盖，无需修改任何内容。
- **`changed`（已更新）**：交付经实测验证的文档、执行脚手架（harness）或功能地图修正（是否提交分支或创建 PR 按用户指令与仓库约定执行）。
- **`blocked`（受阻）**：无法完成覆盖核验，或经证实的修复无法安全落地。必须准确说明受阻原因。

## 编辑范围

仅允许编辑验证技能自身的目录（包括 `SKILL.md`、`features/` 及其所属的任何脚手架脚本）。巡检期间严禁修改产品代码：如果功能地图描述的行为在当前应用中已不复存在，要么属于文档偏离（修复功能地图），要么属于产品回归缺陷（向用户报告，绝不能靠改文档掩盖问题）。

## 执行流程

0. **定位目标。** 找到待维护的验证技能：正文包含启动/驱动章节且附带功能地图的项目本地技能（通常位于 `.agents/skills/verify-*/` 或仓库本地技能目录下）。若有多个候选技能，询问用户维护哪一个；若不存在，立即停止并引导用户使用 `create-verification-skill`，切勿凭空捏造目标。

1. **整理索引。** 阅读功能地图的 `README.md` 并遍历同级文件，修复缺失、多余、重复或失效的条目。保持轻量，不要生成冗长的盘点清单。

2. **源码并发核对（Source wave）。** 为每个功能文件各启动一个并发只读子智能体。每个子智能体从源码出发回答“这个面向用户的功能是如何工作的？”，附带代码引用标出可能存在的文档偏离（drift），并返回一份简练的真实运行验证方法（recipe）。子智能体绝不直接驱动应用，也绝不编辑文件。返回结构为：功能摘要 / 源码入口点 / 疑似偏离或无偏离 / 一份验证操作方法。

3. **汇总协调（Reconcile）。** 收齐每个功能文件的返回摘要后，将重叠的操作方法尽量合并到最少的应用状态中执行。抽查子智能体指出的疑似偏离，无需重复求证已确认无误的描述。排查近期代码变动中新增、但尚未收录进功能地图的用户交互界面；只有在找到确切源码路径时，才能判定某个界面缺失。

4. **真实运行验证（Live pass）。** 即使源码核对看似完全正常，也必须执行真实运行验证。所有驱动操作均由主协调会话完成，并严格遵循验证技能自身定义的启动模型：对于服务端和 UI 应用，串行驱动同一个长驻实例；对于短生命周期的 CLI，每次驱动都启动全新的隔离会话（具体由目标技能的 `Launch` 章节决定，而非本技能）。每个功能至少实际操作一次，且在整个巡检过程中无论遇到何种失败，都必须死守三条不变量：
   (1) 凡是上次出现过异常反应且尚未重新做健康检查的实例，绝不继续驱动：首次驱动前执行 `doctor`，以会话为单位时每个新会话先执行 `doctor`，任何一次驱动失败后再次执行 `doctor`；若遇到 `doctor` 无法察觉的故障（例如进程健康但 UI 卡死），必须重置回已知状态或重启实例，切勿心存侥幸；
   (2) 截至当前采集到的验证证据必须在每次清理后依然完好保留，需到指定路径实地检查确认，不得想当然；
   (3) 任何一次驱动所启动的进程或状态都不得残留到该次驱动结束之后：无论会话是卡死、退出还是共享，每次失败迭代留下的残余状态都必须清理干净（对于共享实例，只清理残余状态，不销毁实例本身）。
   若因验证技能本身过时导致 `doctor` 失败，属于技能偏离：在编辑范围内修复后重试一次（仅重启因该修复而失效的环节，不做多余操作），若仍失败再将本次巡检判定为 `blocked`。对于无法触达的功能，只有在明确列出具体前置条件（认证、权限、操作系统、外部状态）及已尝试路径的前提下，才能标记为 `verified-unreachable`；若功能地图漏写了该前置条件，则属于地图偏离。在问题分流阶段对脚手架做出的任何修复，交付前都必须在真实运行中重新驱动验证。最终销毁（teardown）在整轮巡检的最后一次驱动（包括复测驱动）结束后执行，确保没有任何进程残留（验证证据按技能规定保留）。

5. **问题分流（Triage）。** 用户视角描述有误或缺失，属于文档偏离，直接修复。应用功能正常但脚手架无法驱动，属于脚手架缺口，予以修复；脚手架修复须遵守与生成技能相同的辅助脚本规则（脚本具备可执行权限，且在技能正文中写明调用方式）。应用自身行为确实损坏，属于产品缺陷，如实记录并反馈给用户，绝不混入验证技能修改中掩盖。

6. **交付或终止。** 若结论为 `changed`：先重新通读每个修改过的文件，展示经过真实运行验证的修正（仅在用户明确要求时才自动提交分支与创建 PR）。若结论为 `clean` 或 `blocked`：不做无关写入，如实汇报结论与覆盖情况。

将简明的运行记录（已覆盖功能、不可达前置条件、已确认偏离、最终结论）保存在临时目录中，切勿提交到版本库。
