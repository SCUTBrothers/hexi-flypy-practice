# 给 Agent 写执行说明（writing-for-agents）

动笔前先明确本次编写或修订要改变哪项可观察的 Agent 行为（例如：过去只跑完构建就结束，现在还必须打开导出文件并核对行数）。凡能靠类型检查、测试或脚本稳定拦截的问题，优先用结构性机制兜底，不靠堆砌提示词。

- **入口措辞决定何时读取**：在引用开头使用用户与项目真实出现的词汇，写明触发场景与目标文件用途。每个独立分支只写一次，合并近义表达。若重要材料反复漏读，先调整引用旁的触发措辞并用原请求重测；确认仍会漏读且每次都必需时，再将规则内联回正文。
- **按使用时机分层放置**：各分支都要执行的公共步骤留在正文；需要配套生效的定义、约束与例外放在一起；只在特定分支用到的材料，放到带触发条件的引用文件之后。常驻入口会占用每轮上下文，手动入口则要求人记得主动点名，按实际使用频率权衡。
- **为步骤设可检验的终点**：同时写清完成判定标准和必须逐项覆盖的对象。若 Agent 因提前看见后续步骤而抢跑，先收紧当前阶段的完成标准；只有标准已难以继续细化、且实测仍会抢跑时，才拆到独立会话或子代理（在同一上下文里另读其他文件，后续步骤依然可见）。
- **删掉不改变行动的废话**：沿用项目既有术语，直接写期望执行的动作；确需加硬性限制时，同步给出应该怎么做的替代方案。同一规则只在唯一权威位置维护，配置或 CLI 帮助能低成本查到的信息不必重复抄录。对一句话是否多余存在分歧时，分别用保留和删去它的两版跑同一请求，对照实际行动决定去留。
- **用真实请求做正反试跑**：各挑一个应触发的场景和一个相邻但不应触发的场景试跑，分别核对 Agent 读取了哪些文件、执行了哪些动作、产物能否验收。

编写技能入口或路由技能时，另读 [技能入口与路由机制](./references/SKILL-MECHANICS.md)。
