# 冻结技术规格（to-spec）

将已经完成访谈拍板与代码核查的共识固化为一份面向执行的 `spec.md`。本技能只忠实记录已定决策，不重新开展开放式访谈，也不改写业务代码。

## 前置门禁

- **确认决策已收口**：优先承接 `grill-me`、`architect` 或已有对齐讨论的结果。
- **不脑补阻塞性缺口**：如果发现仍有会实质改变实现方向的未决问题（如核心状态流转、权限边界或接口字段归属未定），停止落盘，集中列出具体缺口请用户拍板或转回 `grill-me`，绝不自行猜测补齐。

## 正文规范

1. **不复述上游文档**：若存在上游需求文档、PRD 或 Issue，只保留路径或链接引用；正文只写增量共识与消除歧义后的可执行结论。
2. **只定契约与架构边界**：写清状态机、数据形态、接口映射、复用约束与错误处理边界；不写逐行伪代码、易变变量名或未核实的代码行号。
3. **标准结构**：
   - 顶层使用合法 YAML frontmatter，固定 `type: spec`（不写 `feature`、`fix` 或 `scratch`，避免误入外部需求索引），按需附 `source`（上游文档路径或链接）与 `branch`。
   - 正文按需包含四个紧凑小节，无内容直接省略，不留空节：
     - **已拍板行为规则**：消除上游需求中的歧义与待确认项，写成可核验的具体条件与结果。
     - **技术决策与接口契约**：选定的模块边界、状态归属、数据流、复用对象与关键接口约定。
     - **不碰范围（Out of Scope）**：明确排除的功能、重构与外部模块，防止下游编码越界。
     - **全局验证方式**：整项改动收口时必须跑通的检查命令、回归测试或端到端核验路径。
   - 行文保持平实紧凑，遵循 `technical-writing`。

## 读写载体与落盘位置

- **外部载体优先**：若当前指令、项目 `AGENTS.md` 或注入规则指定了非本地载体（例如通过 `gh` CLI 写入 GitHub Issues），按该约定执行；向远端平台创建或覆盖内容前，先在对话中展示正文预览，经用户确认后再执行写入。
- **默认本地 Markdown**：未指定外部载体时，按以下顺序确定 `spec.md` 落盘路径：
  1. 用户在当前消息中显式指定的目录或文件路径；
  2. 项目 `AGENTS.md` 或注入规则声明的存放约定（例如关联外部文档目录或仓库子目录）；
  3. 以上均未指定时，写入前先向用户确认目标目录（可建议当前仓库下未纳入版本控制的 `.plans/<slug>/spec.md`），不擅自往陌生仓库创建或提交规划文件。

## 交付检查

落盘后逐项核对：不存在阻塞性的“待确认”占位、未重复抄写上游正文、YAML frontmatter 语法合法。最后返回最终落盘路径（或远端链接），提示用户审阅确认后可用 `to-tickets` 拆解垂直切片。
