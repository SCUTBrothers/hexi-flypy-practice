# 同步当前进展（ketchup）

向用户同步自他们在调用本技能前发出的最后一条消息以来，当前对话发生了哪些变化；不仅要汇报最新状态，还要帮他们看懂每一处变化。随后列出所有等待用户拍板的决策项，让他们单靠你的回复就能直接拍板。系统通知和子智能体返回结果不算用户消息。默认用户只记得自己发出的最后一条消息，对那之后发生的事一无所知。

借用 `bro` 的说话口吻（而非执行它的任务）：用日常词汇、短句、零行话，就像当面给同伴同步近况一样。只说对用户而言变了什么，别说你中间怎么操作的。直接说“测试都过了”，别说“CI 绿了”。除非用户需要凭此采取行动，否则省去提交哈希、文件路径、命令、构建号和测试数量。用用户认得出的名字称呼每个 PR、分支或子智能体，不要生造代号。如果某个事实需要交代背景才能看懂，就把背景补齐，否则干脆省掉这个事实。

## 收集变化

本轮保持只读。只用现有材料制作图示：不要改代码、不要启动应用或新任务、也不要向外发送任何内容。汇总自那条用户消息以来你自己完成的工作、子智能体汇报以及当前对话中其他来源的消息。检查当前对话涉及的每个 PR、检查任务和子智能体的最新状态。把将要展示的每一个数字都与原始事实逐一核对；若修正了之前的数字，明确说明。

行动项（Action item）是指只有用户本人才能做出的决定或操作，例如产品方案取舍、审批放行、不可逆操作，或授予你缺失的权限。凡是仍在等待用户处理的事项都要列入，哪怕是在用户最后一条消息之前提出的。你自己还能继续推进的工作不算行动项。绝不要为了凑内容而凭空编造待决事项。用户未要求且工作本身也不需要的步骤不算行动项；除非该步骤不可逆且正等待用户确认，此时只写一行文字，不配图示。

一项决策可以涵盖多个条目，例如一批等待合并的 PR。针对每个条目收集：链接、给用户带来的变化、支撑你推荐方案的依据、风险，以及你的推荐选择。决策所需但你尚不掌握的事实写“未知”；没有的链接直接略去。

## 撰写回复

把篇幅花在待决事项上，而不是讲过程故事。除图片与图示外，进展概述控制在约 150 字（英文约 100 词）以内；事情少时越短越好。对用户没有任何实际变化的工作一律略去。每个决策条目约 50 字（英文约 30 词），回复篇幅随条目数量自然伸缩：两个条目时整体非常紧凑，三十个条目则需要长得多。绝不要为了凑字数上限而删减条目或压缩关键信息：不准只报总数代替明细列表，也不准丢个链接代替条目内容。链接可以补充深度细节，但回复正文自身必须足以支撑用户拍板。

开头先用简短的一句话点明有哪些事正等用户拍板，或者直接说明没有任何待处理事项；具体细节留到行动项部分展开。如果期间既无新进展，也没有等用户拍板的事，直接说明并就此结束。

接着展示最新进展，画面优先。先把工作中已产出的截图和录屏直接展示出来，再放解释变化原理的示意图。随后针对用户交代的每件事各写一条简短要点：结果如何，目前是已完成、仍在运行、已失败还是尚未检查。每句话都要像当面说话一样自然，例如写“搜索慢是因为漏建了索引”，不要写“搜索排查：完成”或“搜索缓慢：缺失索引”。顺带点明途中发现并顺手修掉的缺陷。每一行哪怕单独拎出来读也必须完全属实。仍在等用户拍板的事项绝不能标为已完成，行动项里会写的内容也不要在此处重复。概述下方最多补充三行会改变用户认知或后续行动的简短信息，最后再用一行说明你自己还能继续完成的剩余工作。

之后列出行动项。明确提出需要用户拍板的决定（如合并、批准或方案二选一），并给出你的推荐。你建议先走的步骤、必须先满足的前置条件以及任何不可撤销的操作，都写进你的推荐意见里。决策涉及的每个 PR、Issue 或子智能体都要附上编号或链接，方案对比时也一样。

按决策形态组织条目结构。只涉及单个条目的决策写成一个列表项：待拍板问题、你的推荐、对用户的改变、推荐依据以及风险，条目名称只提一次。当多个条目共用同一个决策时，先写一次总决策和你的整体推荐，再按风险从高到低为每个条目单独列项：列出名称与链接、对用户的改变、推荐依据及风险；只有当某条目的推荐意见与整体推荐不同时，才单独写明该项推荐。哪怕风险很低也要明确写出，例如“低风险：仅修改按钮颜色”。只有当等待的代价不只是推迟进度（例如会错过截止时间或导致数据丢失）时，才写明等待成本。

当需要在多个方案之间取舍时，列出工作过程中实际权衡过的全部选项，写明各自的收益、代价以及当前所处状态。这些代价本身就是该决策的风险，无需再额外加一行风险说明。如果上方的截图已经展示了各个选项，就把每个选项的收益与代价直接写在对应截图下方。

## 图示（Visuals）

图示是指真正的画面与结构图：已有截图、录屏、Mermaid 图，或已生成的图表。Markdown 表格哪怕带了修改前后对比列，也不算图示。

只要画张图比写几句话更容易看懂，就画出来：比如系统或设计的工作原理、带各 PR 状态的 PR 栈或依赖链、修复前后的效果对比，或者并排摆放的备选方案。绝不要把状态列表、行动项清单或互不相连的孤立框画成图。同一个事实无论在正文还是多张图之间，都不要重复出现两次。

每张图都要精简到一眼能看懂：最多六个节点框，每个框只放简短平实的日常词句，不要写“测试：通过”这种标签体。需要一整句话才能说清的事实只应写在正文里，图里放不下就别放。

凡是肉眼可见的界面变化，若有已截取的截图或录屏应直接展示，不能只给链接；如果某项可见变化还没有截图，就在概述对应行注明“尚无截图”，并在那里直接写明屏幕上变了什么。所有示意图都必须基于已有真实事实绘制，绝不编造数字，也绝不手绘或伪造未曾真实截取的屏幕画面。只链接真实存在的产物。
