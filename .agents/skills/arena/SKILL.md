# 多方案竞赛（arena）

启动任何子任务前，先建立待办清单，每个阶段列为一项（明确任务与评分标准、并行分发、交叉评审、选定基底、嫁接亮点、验证）。

## A 阶段：明确任务与评分标准（Frame）

每个候选方案都会收到完全相同的提示词，因此提示词就是契约。

1. 明确每个候选方案需要产出的具体交付物。
2. 制定评分标准（rubric）：针对**本次**任务写出 3–6 条具体、可打分的成功判定标准。该评分标准仅供 C/D 阶段遴选时使用，各候选方案只能看到任务本身。
3. 选定参评执行者（runners，至少 2 名，默认 2–3 名）。宿主支持多模型时优先选用不同模型家族的子智能体以保证视角多样性；探索多个设计方向时可派生更多执行者；当任务受生成数量限制而非判断力受限时，可将同一模型重复并行运行 N 次。
4. 遵循 `principle-separate-before-serializing-shared-state` 原则技能，为每个候选方案分配独立的输出位置（优先使用独立的 git worktree，否则使用 `/tmp/arena-<slug>/candidate-<n>/`）。

## B 阶段：并行分发（Fan out）

在同一轮并发派生全部 N 个后台子智能体。向每个子智能体传入：任务描述、共享背景材料的路径、各自的独立输出路径，以及要求其产出目标交付物与一份简短设计说明（列出评估过哪些替代方案、淘汰了什么及原因）的指令。

如果某个候选方案未产出结果，继续带着其余 N-1 个方案推进，并记录该掉线（dropout）情况。

## C 阶段：交叉评审（Cross-judge）

待 B 阶段所有候选方案完成后，派生一名只读评审子智能体（宿主支持多模型时优先选用与父会话不同厂商的模型，否则使用未参与生成过程的全新只读子智能体）。当你在 D 阶段通读各方案时，评审子智能体同步按匿名路径标签对照 A 阶段评分标准为各候选方案打分，并给出推荐基底方案；若无可用独立评审模型，跳过交叉评审并在回复中说明情况。

## D 阶段：选定基底（Pick a base）

通读每个候选方案的完整产出后再做抉择。对照评分标准逐条打分，不要凭整体直觉印象定夺；若 C 阶段运行了交叉评审，将你的打分与交叉评审结论横向比对。双方选定同一基底即可确认；若出现分歧，说明必有一方存在偏见或评分标准本身含糊不清，需先读完双方理由再拍板。

优先选择后续维护者最容易扩展、且不易破坏不变量的基底方案。若两个方案难分伯仲，遵循 `principle-laziness-protocol` 原则，优先选择模块边界更清晰或公开 API 更小的方案。

## E 阶段：嫁接亮点（Graft）

重新审视每个落选方案，找出值得移植到基底方案中的设计亮点（通常每个落选方案只取一两处，而非照搬大半）。遵循 `principle-redesign-from-first-principles` 原则技能，手工将每处嫁接内容自然融入基底方案，确保最终产物在同一个心智模型下自洽统一，切忌机械拼贴。

如果各候选方案不约而同收敛到同一种整体结构，说明达成了强共识：记录该共识并直接交付该结构，无需嫁接。如果各候选方案南辕北辙、分歧巨大，说明 A 阶段任务定义不够明确：应当重新界定问题并重跑，而不是把分歧强行折中平均。

## F 阶段：验证（Verify）

遵循 `principle-prove-it-works` 原则技能，严格验证综合后的最终产物。如果验证暴露出竞赛阶段遗漏的问题，要么是 A 阶段任务界定有误（重新界定并重跑），要么是某个候选方案其实已经处理了该问题但你在嫁接时漏掉了（退回 E 阶段补齐），绝不能掩盖问题、敷衍过关。

## 产出物

交付一份综合产物，并附带一份简短的综合说明：写明选定哪个方案作为基底及原因、交叉评审结论（或注明 C 阶段跳过了评审）、每项嫁接内容及其来源候选方案、淘汰了哪些内容及原因、任何收敛或掉线情况，以及最终验证结果。
