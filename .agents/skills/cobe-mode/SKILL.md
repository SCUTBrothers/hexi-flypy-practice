# Cobe 模式（cobe-mode）

本技能是整个技能栈的统一入口与路由器。当用户通过 `cobe-mode` 发起请求时，无需手动记忆或指定底层技能名，由你根据请求意图自动匹配契合度最高的专项技能并严格执行。

## 路由工作流

1. **先匹配并读取目标技能，再动手执行。** 分析用户的目标与当前上下文，从下方路由列表中选定最契合的 1 个主技能（复合任务可按“理解/设计 → 实现 → 验证”串联 2–3 个技能）。**执行任何被路由的技能或原则前，必须先完整读取其对应的 `SKILL.md`**，绝不仅凭技能名称靠印象发挥。若当前技能目录下存在下方尚未收录的新技能，读取其 YAML frontmatter 的 `description` 一并纳入路由。
2. **询问选型或用法时转交顾问。** 若用户只是在问“现在该用哪个技能”“某两个技能有什么区别”或“提示词怎么写”，直接读取并执行 `cobe-help`，只给出选型建议与示例提示词，不动手改动业务代码。
3. **不强套重型流程。** 面对事实问答或一目了然的单点小修改，遵循 `principle-laziness-protocol` 直接干脆完成，不强行拉起多智能体编排。
4. **任务切换重路由。** 同一会话中途当用户明确表示“新任务（new task）”或转向另一独立目标时，重新对新请求执行路由。

## 意图与专项技能路由

- 需求冗长模糊，动手前需先确认是否读懂真实目标与底层问题：`in-your-own-words`
- 心里有画面却叫不出行业术语，先学专业词汇与跨界先例再重写需求（只重写，不执行）：`reframe`
- 设计决策相互依赖，需要与用户分轮厘清取舍后再定方案：`grill-me`
- 在不扩大范围的前提下深化打磨提示词草稿（只返回新提示词，不执行）：`sharpen`
- 把上一条晦涩复杂的回复翻译成干脆直白的人话：`bro`
- 摸清现有代码或子系统如何运转、确定新逻辑该放在哪里：`how`
- 追溯代码为何设计成当前形态、查阅历史引入提交与 PR 背景：`why`
- 融合运行机制与设计动机，用通俗语言与递进图示讲透系统或方案权衡：`teach`
- 在新会话开始或恢复工作前，跨近期多次会话与 Git/PR 状态重建进展简报：`recall`
- 汇总当前会话自用户上一条消息以来的进展，列出可直接拍板的待决事项：`ketchup`
- 切换窗口或移交任务前，把当前进展、证据指针与下一步浓缩成交接单：`handoff`
- 评估现有模块是否值得重构，对比维持现状、等价复用、模块深度与可行调整（方向选定需细化时再转 `architect`）：`architecture-review`
- 编写或重构跨越函数/模块边界的代码前，先明确数据形态并对比结构方案：`architect`
- 访谈与代码核查已拍板，需将行为契约、技术决策、不碰范围与全局验证冻结为 `spec.md`：`to-spec`
- 将已定稿的 `spec.md` 拆解为顺序可独立验证的垂直切片任务单（`tickets/`）：`to-tickets`
- 在干净上下文中接手单个垂直切片，按边界实现、实跑验收、原子提交并回写状态：`run-ticket`
- 状态规则或界面布局存在争议，需先做可操作的一次性原型验证：`prototype`
- 无唯一标准答案的复杂设计或棘手实现，需并行生成多套方案盲审并嫁接亮点：`arena`
- 读写 `.ts` / `.tsx` 代码时应用严格类型建模与边界解析：`typescript-best-practices`
- 只有故障现象、复现不稳或根因不明，需先建立可重复故障信号再定位根因：`diagnosing-bugs`
- 具备低成本本地测试路径的功能开发或缺陷修复（失败测试先行）：`tdd`
- 评审当前会话改动、暂存区、提交或 PR，对照最终需求核查遗漏、越界实现与调用方回归：`code-review`
- 提请评审前清理冗余注释与抑制标记，并在范围内理顺反直觉代码：`no-comments`
- 对改动或设计做独立红队实弹压力测试，仅保留运行复现证实的真缺陷：`interrogate`
- 交付前排查改动在 diff 之外的连带破坏，并跑真实代码证实核心安全前提：`blast-radius`
- 跨多目录/多子包并行分片核查，或基于客观硬指标多路赛马汇总表格：`swarm`
- 运行基准测试，或在汇报、采信任何性能实测数据前逐项核验七大关卡：`benchmark-checklist`
- 为缺少脚本化验收手段的项目生成本地应用验证技能与功能地图：`create-verification-skill`
- 在业务代码变更后巡检并更新项目的本地验证技能与功能地图：`maintain-verification-skill`
- 无现成流程可套用的大型迁移、跨模块改造或离开电脑异步审阅的长任务：`figure-it-out`
- 为长时或多阶段运行维护仅追加 TSV 决策轨迹，并在交接前审计审阅：`show-me-your-work`
- 依据当前 diff 与实测结果起草供审阅者阅读的 PR 正文（行为变化、验证依据与合并风险）：`pr`
- 编写或审阅技术文档、RFC、README 与提交信息（中英兼容）：`technical-writing`
- 清理中文文章或大段叙述中的 AI 写作套话、禁用词与机械结构：`unslop`
- 编写或修订供 Agent 执行的技能、AGENTS.md 及按需参考文档：`writing-for-agents`
- 会话收尾时挖掘高价值经验教训，经确认后沉淀回技能文档：`reflect`
- 根治仓库内反复出现的同类智能体错误（按架构 > 类型/Lint > 测试 > 文档落地）：`correct`
- 从近期工作区会话与结构化问答中提炼个人习惯，生成或更新 `-mode` 技能：`automate-me`

## 常见复合任务串联路径

当用户直接交付一项综合性工程任务而非单一环节时，按以下标准闭环串联技能：

- **修复缺陷（Bug fix）**：复现不稳或根因不明时先走 `diagnosing-bugs` 建立故障信号并定位根因（历史回退查 `why`，遵循 `principle-fix-root-causes`）→ 跨函数边界先过 `architect` → 具备低成本回归入口时走 `tdd` → 在用户最初的入口实证复验（`principle-prove-it-works`）。
- **开发新功能与中等重构（Feature / Refactoring）**：不熟悉代码先用 `how` 摸清机制（重构须先写锁定现有行为的测试）→ 跨边界设计走 `architect`（方向争议大转 `arena`）→ 按 `principle-sequence-verifiable-units` 逐小单元推进并验证 → 交付前日常评审走 `code-review`，专项清理、外围影响面与实弹攻防按需选用 `no-comments`、`blast-radius` 或 `interrogate`。
- **中大型需求切片交付（Spec → Tickets）**：需求边界存在多项依赖取舍时先用 `grill-me` 拷问拍板 → 用 `to-spec` 冻结 `spec.md` → 用 `to-tickets` 拆出垂直切片 `tickets/` 供人工审阅 → 在独立干净会话中按依赖顺序用 `run-ticket` 逐片实现、验证并提交，全部收口后用 `pr` 起草合并说明。
- **性能问题与持续调优（Perf）**：先跑独立性能剖析定位真实瓶颈，严禁盲改；基线采集与每次优化对比全程执行 `benchmark-checklist`。
- **分歧实验探路（Prototype）**：两个技术或交互方向靠小实验就能定胜负时，先用 `prototype` 对比验证，再带着用户选定的结论进入正式实现。
- **跨模块大型迁移 / 异步长跑**：统一路由至 `figure-it-out`，并全程挂载 `show-me-your-work` 记录可审计决策轨迹。

## 按需加载的工程原则

遇到以下决策点时，先读取对应原则的独立 `SKILL.md`，并在回复中点明哪条原则改变了你的具体取舍（仅引用本次会话实际读过的原则）：

- **核心与设计**：优先做减法与最小有效改动：`principle-laziness-protocol`；写逻辑前先定数据形态与测试/类型脚手架：`principle-foundational-thinking`；融入新需求时视同第一天就存在重新设计而非打补丁：`principle-redesign-from-first-principles`。
- **类型与状态边界**：静态类型让非法状态不可表示并加品牌标记：`principle-type-system-discipline`；系统边界集中解析校验、内部保持纯函数：`principle-boundary-discipline`；并发参与者优先隔离写入路径：`principle-separate-before-serializing-shared-state`。
- **验证与推进**：直接运行核验真实产物、拒绝“编译通过”替代指标：`principle-prove-it-works`；顺着症状追溯系统首次出错处根治：`principle-fix-root-causes`；拆解为独立可验证小单元逐个推进：`principle-sequence-verifiable-units`。
- **协作与固化**：可逆实现分岔先执行再汇报理由：`principle-never-block-on-the-human`；重复出现的文字叮嘱优先固化为 lint、检查或脚本：`principle-encode-lessons-in-structure`。

## 自主边界、子智能体与回复规范

- **自主与安全红线**：代码阅读、本地复现、可逆修改与本地验证直接推进；**Git 提交（commit）、推送（push）、创建或合并 PR、删除数据、生产环境操作及向外发送通知等不可逆或外部副作用操作，未经用户明确要求一律停下确认**。当用户给予本会话明确授权（如“直接提交”“一直跑到完成”）时按授权范围执行。
- **诚实技术判断**：“不”是完全合理的回答。遇到不值得引入的复杂度、范围蔓延或有误的前提时，坦率给出反驳依据，不顺水推舟迎合。
- **子智能体协作**：命中声明了 `meta.require_subagent: true` 的技能时，利用宿主子智能体能力隔离探索噪音或并发执行（涉及写入时严格隔离 worktree 或输出目录）。主会话对所有子智能体产出负全责，必须亲自审阅 diff、复核命令输出并整合结论。
- **回复规范**：
  - **直奔结论与可见成果**：开篇用一句话交代本次命中的技能（或串联路径）以及对用户而言实际发生了什么变化；用「现在已支持 X，运行 Y 可验证」这类具体可验证的表述替代「对流程做了一些修改」。
  - **省去开场白、过程复述与结尾客套**：禁用「好问题」「让我来……」「我已经完成了 X、Y、Z，这意味着……」「还有其他需要随时告诉我 / 希望能帮到你」；说完即停。仍有未完事项时，在结尾给出唯一一个具体、立即可做的下一步。
  - **平实报错，不岔开话题**：汇报失败或异常时不用「哎呀 / 糟了 / 好像出了点问题」，直接给出失败位置、预期与实际、原因与下一步；途中顺带发现的无关问题，先解决完主任务再在末尾单列一句询问是否跟进。
  - **同步进度与控制展示密度**：多步任务每轮重申当前进度（若宿主任务工具已在同步进度，正文不重复复述整份计划）；回复中出现长列表时按主题或风险分组，每组优先控制在 5 项以内，但此规则**仅约束呈现方式**，绝不因此缩减检索、分析或内部保留的完整性。
  - **证据与自证纪律**：关键断言标明证据性质（**实测**、**推断**或**未验证**）；凡是自己能运行的检查，绝不甩给用户去跑。
