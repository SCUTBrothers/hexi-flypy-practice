# 用测试驱动缺陷修复（tdd）

修复具备清晰、低成本测试路径的缺陷时，在改动生产代码之前，先把出错行为写成可执行的检查。目标是写出一个精准聚焦的回归测试：**修复前稳定失败，修复后稳定通过**。

当写测试不切实际时，绝不硬凑。如果测试需要沉重的脚手架搭建、脆弱的 mock、缓慢的端到端基础设施、仅线上才有的状态、模糊的复现步骤，或大面积改动无关测试夹具，应跳过新增测试，改用最贴近目标的有效验证手段。

## 工作流

1. **摸清缺陷。** 明确预期行为、当前实际行为、受影响的代码路径，以及最小可观察复现条件。
2. **选最窄的可执行检查。** 优先复用该代码路径已有的单元、组件、集成或回归测试体系；若没有现成实用的测试入口，不要为了走形式从零搭一套框架。
3. **先写失败测试。** 添加能捕获该缺陷的最小聚焦测试。测试断言应当表达预期行为，而不是照抄当前内部实现。
4. **修复前先运行新测试。** 确认它确实因预期原因失败；若直接通过或因无关报错失败，先修正测试或复现条件，再碰业务实现。
5. **修复缺陷。** 用最小的生产代码改动满足预期行为，同时保持周边契约不变。
6. **重跑回归测试。** 确认新测试现已通过。

## 当写失败测试不切实际时

改用最接近的可执行回归检查：定向验证脚本、复现命令、浏览器/UI 自动化断言、快照比对、日志断言或聚焦的集成检查。

宁可不加新测试，也不要写烂测试。烂测试的典型特征：大半代码在测 mock、锁死当前内部实现细节、依赖脆弱时序或无关全局状态、为一行小修引入高昂基础设施，或验证完修复就得立刻删掉。

## 护栏

- 绝不为了迁就错误实现而去篡改测试预期。
- 除非预期业务行为确实变更且理由清楚，否则绝不削弱已有断言。
- 回归测试严格聚焦于当前缺陷，避免大面积折腾无关夹具或顺手扩充无关覆盖率。
- 若属于偶发缺陷（flaky），尽量把测试写成确定性可复现，并注明锁定的具体信号。
- 若该缺陷暴露出一整类同类问题，先把当前聚焦回归路径合入跑通，再考虑补充相邻用例。

## 最终回复

报告真凭实据，而非只报结果：

- 说明修复前运行的失败测试（或可执行检查）及其实际输出的失败信息。
- 说明修复后通过的测试运行结果及连带执行的周边验证。
- 若确实无法展示修复前失败证据，说明原因，并交代实际采用了哪种替代回归检查。
