# 排查难以复现的故障（diagnosing-bugs）

从用户可观察的故障现象切入，先写清触发条件、预期行为与实际结果。若项目维护了术语表或架构决策记录（ADR），可借此确认模块边界。命令、日志与回放数据仅保留脱敏后的必要片段，凭据一律留在环境中。

## 1. 建立可重复的故障信号

挑选能触及故障的最短真实入口。优先选用现有测试、本地 HTTP 请求、固定输入的 CLI 输出对比或浏览器交互；复杂场景可采用脱敏事件回放、最小调用脚本、固定随机种子输入、在已知好坏版本间二分定位，或用同一输入对比新旧结果。若确需人工介入操作，复制 [人工复现脚本](./scripts/hitl-loop.template.sh) 并改写为具体步骤，请用户输入实际观察结果。

给出实际执行过的命令与脱敏输出，确保该检查在故障重现时稳定失败、在行为正常时通过；尽量将单次耗时压缩到数秒内并复跑确认。面对偶发故障，先记录失败次数与总次数，再通过重复触发、控制并发顺序或固定时钟与随机种子拉高复现率，并记下可重跑的条件。在拿到可靠的故障信号前，阅读代码只为找到可运行的入口，不要凭空猜根因。若尝试多种入口仍无法复现，如实说明已试路径，请用户补充可复现环境或最小脱敏样本。

## 2. 缩小范围与验证假设

1. **精简复现条件**：逐一去掉无关的输入字段、操作步骤或依赖，每删一项都重跑确认。最终留下的每个条件，去掉任意一个都应使原症状消失；偶发故障则对比删减前后的复现率。
2. **提出可证伪假设**：动手验证原因前，向用户列出按可能性排序的 3–5 个可证伪假设，每项写明准备改变什么条件、预期会看到什么结果；用户暂未回应时可直接推进验证。若已有直接证据足以跳过对比，说明哪项实测已把其他可能排除；跳过其他步骤时也同样说明理由。
3. **定点观测定位**：每个探针只对应一项预测，每次只改变一个变量。优先使用断点或局部观测；若需加临时日志，统一带上本次排查专属的标记（如 `[DEBUG-a4f2]`）方便事后清理。涉及性能回退时，先按 `benchmark-checklist` 在同一负载下建立基线，再结合计时、性能剖析或查询计划缩小范围。存在已知好坏版本时，用同一检查做二分定位；需追溯引入改动的历史背景时，使用 `why`。
4. **连续受挫及时熔断**：若连续三轮定位或试修后故障依然存在，立即停手，不再继续盲改代码；回过头指出哪项前提假设可能有误，并向用户提出一个聚焦的诊断性问题。汇报失败时保持平实客观，直接给出失败位置、预期与实际、原因与下一步。

## 3. 修复、复验与清理

追查到错误状态首次出现的位置，按 `principle-fix-root-causes` 确认修复点。需要实施修复时，选用能还原真实调用关系的测试入口（例如两个调用方共同触发的故障，须让它们走过同一个共享状态），用最小复现按 `tdd` 先跑出失败再改代码。若复现依赖临时改动代码或构造样本，须先与干净副本对照，确认改动确实生效。现有测试入口覆盖不到该路径时，明确指出缺失的测试接缝，并保留仍有用的复现命令。若用户只要求诊断，则交付根因、证据与建议修复位置，不改业务代码。

修复后先重跑回归检查，再回到最初的真实入口用未经缩减的完整场景复验（偶发故障须附上修复前后的复现次数）。向用户报告已证实的根因；若需用于提交信息或 PR，将根因一并写入。最后按本次专属标记检索残留日志，彻底清理临时探针与一次性样本，仅保留复验所需的命令或正式测试。
