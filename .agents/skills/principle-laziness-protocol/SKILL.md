# 精简优先（principle-laziness-protocol）

- **审慎收敛共同决策**：确认多处入口执行的是同一条业务规则、且未来必然同步演进后，再将判断收拢到单一事实来源并向下传递结果。外表相似但分属不同业务契约的分支（例如前端展示文案与对外协议字段），各自保持独立。
- **按成本由低到高选方案**：从用户确认的真实需求出发，砍掉面向假想需求的扩展点、多余配置与无意义中转层。寻找实现时依次排查「项目已有实现 → 语言标准库或平台原生能力 → 已安装依赖 → 少量自有代码」，找到合适的就停手。沿用项目既有分层与平台原生值类型，几行清晰代码就能解决时不引入新依赖；同等改动量下优先选择能自然处理边界值的写法。复用既有实现前，逐项核对默认值、校验、错误处理与副作用。
- **精简不等于偷工减料**：全局检索受影响的调用方、导出符号、配置、测试与样本，在共享逻辑处一次修透，并从真实入口验证完整行为。必须保留信任边界校验、防数据丢失的错误处理、安全防护、无障碍支持与必要的硬件校准。凡涉及复杂分支、数据解析、持久化写入或缺陷修复，都应有能抓出错误的既有检查、聚焦测试或断言兜底。
- **尊重既定任务范围**：用户已明确指定实现方式时，若发现更轻量的替代方案，用一句话交由用户选择；用户只给目标时，直接采用完整且最简的实现；只有当用户明确邀请挑战范围时，再指出哪些需求缺乏实际用途。交付时如实交代影响使用的取舍与尚未核验的条件。
