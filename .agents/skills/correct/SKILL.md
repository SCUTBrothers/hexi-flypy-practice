# 根治反复出现的错误（correct）

操作者在本仓库里不得不一再纠正智能体的同类错误。请直接改造仓库本身，让下一个智能体根本无法再犯这些错。

假设每一位后续贡献者都是只能看到自己打开的那几个文件、会照抄最近示例、并走最短编译通过路径的智能体。把仓库设计成“单看一个文件似乎正确的改动，放在整个仓库里也确实正确”。

## 1. 归纳错误类别

先读取近期提交、回滚记录、评审意见、智能体指令文件（如 `AGENTS.md` / `CLAUDE.md`）以及解释临时绕行写法的注释。将错误聚类归组；同一类错误出现两次即纳入治理。

## 2. 在能生效的最高层级根治每类错误

1. **用架构消除错误。** 让每份状态只有唯一归属，每项任务只有唯一受支持的做法。隐藏内部模块使错误导入直接失败；用单一事实来源替代手工同步的多份列表；删掉智能体会照抄的旧写法与死代码。
2. **用类型约束让错误状态根本写不出来。** 若错误代码仍能通过编译，就添加一条报错信息直接点明替代文件、类型或函数的 lint 或 CI 检查；若存量代码已大量存在该旧模式，先配置为仅拦截新增违规。
3. **测试外部可观察行为。** 修复或删掉“被测行为已坏却仍然通过”或“仅改内部实现就挂掉”的失真测试。
4. **文档或智能体规则排在最后，仅用于真正的判断权衡。** 智能体忽略文档时没有任何机器检查会报错。

## 3. 修复并实证

立即动手修复最高频的错误类别，每类独立一个提交。必须证明每项新增检查在真实的历史错误样本上确实会失败报错，且在本地与 CI 运行同一条命令。确需豁免的例外写在违规行旁，附明原因、过期日期与人工批准记录。

## 4. 维护规则与强制机制对照表

最后，在仓库的智能体指令文件中维护一张对照表，将每条规则与强制执行它的机制配对。每当操作者纠正你时，修复问题并同步登记规则；若表中已有该规则却没有任何机制强制执行，说明发生了重复违规，必须在本次改动中将其提升到最高可执行层级。一旦某类错误已在架构上不可能发生，立即从表中删掉对应条目。

**回复：** 逐类列出历史证据、选定的治理层级，以及更高一层级为何不适用。
