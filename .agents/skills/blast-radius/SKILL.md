# 评估影响范围（blast-radius）

在代码交付前，查明改动可能在其他地方引发的连带破坏。适用于“X 的影响范围”“这会破坏什么”，或审阅一份看似很小、但心里没底的 diff。

本技能与 `how`、`why` 互为配套：`how` 解释代码怎么运作，`why` 解释代码为何长这样，而 `blast-radius` 专门查明改动会在别处破坏什么。

光把调用方列出来不算完成任务。智能体用 `grep` 一秒钟就能搜完。真正的任务是找出那些 **`grep` 根本搜不出来的连带破坏**。

## 别轻信自己写的分析报告

一份“听起来头头是道”的影响范围分析报告毫无价值，不管结论是对是错，文字读起来都会很像那么回事。因此，不要光交差一份分析报告：找出整件事之所以安全所依赖的那一两个关键事实，并**通过运行真实代码来证明它们**。

### 你的确信度处在哪一级

对于改动安全性所依赖的每一个关键事实，在成本可控的前提下，尽量沿着下面这张表往下推进到最高验证等级，并明确交代你停在了哪一级：

1. **口头断言**。全凭嘴说，本身毫无价值。
2. **指出代码行**。给出真实的 `file:line`，或所调用三方库自身的源码位置。
3. **推演排除故障路径**。一步步推演故障触发路径，证明坏情况在逻辑上不可达。
4. **实际运行代码**。编写调用真实代码的脚本或测试，一旦你的假设有误就会直接报错失败。
5. **在运行中的应用里复现验证**。

第 4 级通常只需要写一个小脚本：直接导入应用实际打包的同一个库，调用你担心的那个具体函数即可。

## 执行步骤

1. **读懂改动内容**。仔细阅读 diff，看清新增、修改和删除了哪些符号，以及行为发生了什么变化，尤其是 diff 字面上没有直接写出来的隐含行为变化。拉取关联 PR 及其提交记录。
2. **找出支撑安全性的唯一核心事实**。大多数看起来有风险的改动之所以安全，往往只依赖于某一个关键事实（例如“这次调用只会清理已经失效的缓存条目，不会触碰其他任何状态”）。全力找出这个核心事实，只要它成立，大半疑似风险就会瞬间排除。把精力花在验证这个核心事实上，不要列一长串模棱两可的“可能”。
3. **深挖 `grep` 止步的地方**。去读你所调用的三方库源码，核对其锁定的版本号与本地补丁（patch）。算清楚代码的执行时机：微任务队列（microtasks）、组件卸载与清理（unmount & teardown）、不同框架生命周期差异。顺着符号搜索找不到的线索往下追：API 返回的 JSON 字段、数据库列、线协议格式（wire format）、读取同一串字节的另一门语言服务、特性开关（feature flag），以及下游三跳开外的消费方代码。
4. **如实评估每项风险**。给出每项风险真实发生的概率与一旦发生造成的实际代价。保留经核实确有风险的项；将排查过并已排除嫌疑的项单独列出。引用真实的 `file:line`；搜索结果为空本身也是有效结论；绝不凭空捏造调用方或 API。
5. **用代码证明核心事实**。编写一段调用真实代码的脚本或测试，跑一遍，并把实际运行输出贴出来。
6. **大范围改动直接上 `arena`**。对于波及面广的大型改动，用 `arena` 方式运行：向多个执行者提出同一个问题并汇总答案，不同模型往往能抓出不同侧面的真实缺陷。

## 交付格式

- **改动实质（What it does）**。到底改了什么，包括表面上不明显的变化。
- **支撑安全的核心事实（The one fact it's safe because of）**。明确写出该事实、交代你推进到了第几级验证，并贴出实证输出；若无法证实，直接标明“未证实（unproven）”。
- **确认的风险（Risks）**。逐条说明如何触发破坏、对应的 `file:line`、发生概率与危害程度，以及排查验证方式。重要风险必须贴出实证。
- **已排除项（Cleared）**。排查过哪些地方，以及为什么它们不会受影响。
- **合并前必做（Before you merge）**。能拦住真实缺陷的最低成本测试或复现手段（包括你刚才编写的验证脚本）。

全文通过 `unslop` 清理表达，引用真实代码位置，并在发布到任何公开场合前剥离所有敏感私有信息。

**回复：** 输出上述结构化报告，且核心安全事实必须处于“已证实”或明确标记为“未证实”状态。
