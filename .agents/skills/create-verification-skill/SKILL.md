# 创建项目验证技能（create-verification-skill）

每个严谨的项目都需要一套脚本化手段来驱动真实应用并验证其行为：启动应用、像真实用户一样操作功能，并采集证据。本技能会针对当前仓库量身生成一项项目本地技能（默认存放在 `.agents/skills/verify-<app>/`，若仓库已有统一本地技能目录则沿用该目录）。生成器的输出是写给下一个智能体看的，而非写给人类：从未见过该应用的智能体将在任务中途直接上手阅读它。

## 1. 调研仓库，而非盘问用户

先从代码库中寻找以下问题的答案，仅向用户追问无法从代码中观察到的信息：

- **交互界面（Surface）：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用还是代码库（library）？一个仓库可能有多个交互面，选出主要界面并记录其余部分。
- **运行方式（Run）：** 应用如何在本地启动？优先采用仓库自身文档记载的开发启动命令（`package.json` 脚本、`Makefile`、`README` 快速入门）。留意端口、环境变量、种子数据（seed data）和认证方式。
- **驱动方式（Drive）：** 智能体如何以编程方式与之交互？优先复用现成的执行脚手架（harness）：Playwright/Cypress 测试规格、`expect` 脚本、PTY 辅助工具、可 `curl` 调用的端点或调试端口；若无现成工具，再选择通用方案：Web 与 Electron 用浏览器/CDP，CLI/TUI 用 `tmux`/PTY 脚手架，后端服务用纯 HTTP。
- **观测方式（Observe）：** 可以采集哪些证据？屏幕截图、终端会话记录（transcript）、响应体、日志、退出码、数据库状态。
- **隔离性（Isolate）：** 能否并行运行两个实例（通过隔离端口、数据目录、配置文件）？若不能，必须在生成的技能中明确写明：宁可拒绝并发驱动共享实例，也绝不能破坏用户的当前会话。

如果当前检出的代码无法原样构建或启动，先修复该问题（或准确报告原因）再生成技能；基于损坏基线编写的技能只会传授错误步骤。若阻碍启动的是无关紧要的缺失资源（例如 API 根本不会提供服务的静态目录或示例配置文件），生成的技能可以自行创建该资源，但需明确标记为验证脚手架产物，并在清理阶段将其删除。

## 2. 生成技能

编写 `.agents/skills/verify-<app>/SKILL.md`，顶部包含 YAML frontmatter（设置 `name: verify-<app>`，并在 `description` 中指明应用名称、交互界面及使用时机；缺少 frontmatter 技能将无法被宿主识别），正文包含以下章节，每节内容均须扎根于实际调研结果（不留任何占位符）：

- **启动（Launch）：** 启动应用以供验证的确切命令，以及判断应用就绪的依据（特定日志行或提示符）。启动流程必须能从空数据目录达到可用状态，包含必要的迁移和种子数据。“就绪”意味着真正可用，而非仅仅进程有响应（当数据库初始化脚本仍在运行时，健康检查可能早已通过）。同时写明销毁（teardown）步骤。对于短生命周期的 CLI 或 TUI，没有需要保活的服务端：启动即构建一次二进制文件（或安装依赖），随后每次驱动都在各自隔离的 PTY 或 `tmux` 会话中启动。
- **健康检查（Doctor）：** 一项只读检查，用于回答“当前实例是否适合驱动？”：进程存活、版本/构建号正确、端口归当前任务所有、认证有效。一旦发现任何异常，智能体应首先运行此检查。
- **驱动（Drive）：** 使用当前仓库真实选择器或命令的脚手架操作方法（recipe），而非虚构示例。优先采用稳定的定位句柄（ARIA 标签、`data-*` 属性、提示符字符串、路由路径），避免依赖屏幕坐标或 Tab 键顺序。
- **证据（Evidence）：** 验证证明需采集哪些内容、存放在何处。明确证明标准：必须走真实用户路径，不得调用内部 setter 或仅限测试的端点；同时采集操作过程与结果状态，而非仅截取最终画面；除界面可见内容外，还需核验副作用（写入的文件、插入的数据行、发送的消息）；仅在生产边界本身已隔离外部系统时才允许使用 mock。若安全路径依赖 dry-run 或测试模式，需通过实际观测（文件、网络、Git 引用）核实它究竟跳过了哪些操作，切勿轻信模式名称（有些 dry-run 仍会访问网络或打开浏览器）。
- **清理（Cleanup）：** 如何销毁本次运行创建的实例。严禁按进程名强杀；只终止自己启动的进程。清理操作仅移除运行实例与临时状态，绝不删除证据：验证产物必须在销毁后依然保留在技能指定的位置。
- **辅助脚本（Helpers）：** 技能随附的任何脚本都必须具备可执行权限，并在技能正文中展示调用方式。需要读者逆向工程才能弄懂的脚本算不上辅助脚本。

## 3. 初始化功能地图

创建 `.agents/skills/verify-<app>/features/README.md`，并为识别出的每个面向用户的功能各建一个文件（起步阶段先从路由、命令、菜单或文档中提炼前 3～5 个核心功能）。参照 [references/feature-map-example/README.md](./references/feature-map-example/README.md) 的目录结构，由一个 `README` 索引和每个功能独立的文件组成。每个文件从用户视角回答：该功能是什么、如何进入、如何用脚手架驱动，以及什么样的可观测终态能证明其正常工作。四个二级标题固定为 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某条操作路径所需的前置条件，该路径应如实报告失败，并将原因记入该功能的 `Gotchas`；绝不能为了强行通过而削弱验证流程。功能地图是仓库持续维护的验证基准；当功能地图列出了多个入口点时，只挑一个省事入口进行驱动的验证是不完整的。

## 4. 交接前实测生成的技能

将生成的技能指令端到端完整执行一遍：启动、健康检查、驱动**一个**已映射的功能（跑通一个即可；功能地图存在的意义就是让后续运行覆盖其余功能）、采集证据、执行清理。清理完成后，确认证据依然存在于指定位置；若清理过程吞掉了验证证据，则本步失败。修复失败项，且每次失败迭代后同样要运行生成的清理流程，防止失败尝试遗留孤儿进程或占用端口。从未执行过的生成技能只是草稿，不能算作交付物。如果是在真实目标环境的替身环境（例如用容器代替全新虚拟机、用本地服务栈代替远端服务栈）中完成验证的，必须列出替身环境已执行、但真实目标环境不会执行的每一个准备步骤。在真实目标环境实际跑通之前，这些步骤均视为未验证。

## 5. 提供维护闭环

引导用户使用 `maintain-verification-skill`，以便在应用变更时持续保持功能地图准确。仅在用户主动询问时才给出维护频率建议。
