# Notes 验证功能地图

本目录是验证 Notes 应用面向用户行为的持续维护基准。驱动应用前请先阅读本索引，再将对应的功能文件作为操作方法（recipe）执行。

## 基线前置条件

- 使用一次性数据目录在 `http://127.0.0.1:4173` 启动 Notes。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，使并发运行互不共享状态。
- 预置标题为 `Quarterly plan` 和 `Grocery list` 的种子笔记。
- 将 `control-notes` 和 `notes` CLI 加入 `PATH`。
- 运行 `control-notes doctor`，确认返回预期的 URL、数据目录和构建版本号。
- 严禁驱动非本次验证运行所启动的实例。

## 驱动约定

- 除非前置条件另有说明，每套操作方法均从基线状态开始。
- 优先使用 ARIA 角色（role）与无障碍名称（accessible name），而非 CSS 选择器或 DOM 位置。
- 严格按字面执行每条命令，保持引号内的名称与参数标志不变。
- 浏览器操作通过 `control-notes browser` 执行。
- 终端操作通过 `control-notes cli -- <command>` 执行。
- 执行写操作后恢复种子数据。清理期间不得删除验证证据产物。

## 证据采集与跳过报告

- 同时采集用户操作和结果状态，而非仅保留最终画面。
- UI 验证证据须包含 ARIA 快照，以及能看清应用标识的屏幕截图。
- CLI 验证证据须包含执行命令、`stdout`、`stderr` 和退出码。
- 写操作验证证据须包含从第二个只读视图确认已保存值的证明。
- 每份证据产物均须记录所使用的功能 ID 和入口点。
- 报告不可达路径时，须附带已尝试的命令和未满足的前置条件。
- 不得将已跳过的入口点报告为“已通过其他路径验证”。

## 功能文件结构约定

每个功能文件均以一级标题（H1）和一段描述用户可见行为的文字开头，随后严格按以下顺序包含四个二级标题（H2）章节：

1. `Sub-features`：列出简短的功能 ID，每行描述一项具体行为。
2. `How to get to it (user POV)`：列出每一个用户入口点。
3. `Driving it with <harness>`：以 `Preconditions:` 开头，随后使用带标签的列表项，将每步用户操作与确切命令及可观测结果一一对应。
4. `Gotchas`：列出可能导致验证运行白费或失效的常见陷阱。

功能地图中不要混入实现细节，只写明用户路径、稳定句柄、所需状态、执行命令和可观测证据。

## 功能列表

- [创建笔记](./create-note.md)：涵盖浏览器端与 CLI 端的创建、取消、持久化及清理。
- [搜索笔记](./search.md)：涵盖工具栏、快捷键与 CLI 搜索，包含匹配结果、空结果及清除查询状态。
