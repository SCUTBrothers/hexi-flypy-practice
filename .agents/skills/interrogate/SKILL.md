# 对抗性评审（interrogate）

由对手子智能体设法破坏目标改动或设计。**任何发现项唯有通过实际运行证实才准存活。** 只报告发现项，不动手修改业务代码。

## 界定范围与意图

审查范围优先采用用户指定的范围；未指定时，取当前分支相对于基准分支合并基点（merge base）直至工作树的完整 diff。根据用户消息、提交记录与 PR 描述，按 `in-your-own-words` 技能陈述本次改动的真实意图；意图不明时先询问用户。

## 并行分发

执行 `arena` 技能的 A 阶段第 3、4 步与 B 阶段，但做以下三处调整：将审查范围内的未提交改动同步复制到每个独立工作树中；不传入常规任务与设计说明要求，改为向每个对手子智能体传入审查范围、改动意图以及以下简报：

> 设法攻破这项改动。每一条发现项都必须通过针对真实代码的实际运行来证明（如失败的测试、复现脚本或展示错误行为的命令输出）；若是设计或计划，则运行最小原型或探测当前代码树。复现材料保留在你自己的工作树内。按统一要素报告每条发现项：标题、精确执行命令、实际打印输出，以及改动意图所要求的正确输出。**凡是你没有亲自运行验证过的内容一律不准写**——这自动排除了代码风格、命名偏好、结构挑刺以及“以后万一怎么改才可能出问题”的假想风险。零发现是完全有效的结论。

## 逐条复核

按 `arena` F 阶段的方式，亲自重新运行每条发现项给出的命令进行核验。只有当输出确实复现了失败、且该失败真正违背了改动意图时，才保留该发现项；其余一律丢弃。合并共享同一根因的发现项。

跳过 `arena` 的 C、D、E 阶段。不同对手会抓到不同侧面的真实故障，因此最终结论保留**每一条经运行核实的发现项**，而非只取某一个对手的清单。

## 输出格式

- **改动意图（Intent）**：复述的意图。
- **已核实发现项（Findings）**：逐条列出复现命令、实际输出、如何违背了意图，以及抓出该问题的对手标识；若无任何发现项存活，直接写“无经运行证实的发现项”。
- **已丢弃项（Dropped）**：按每个对手统计丢弃的发现项数量及丢弃原因。
