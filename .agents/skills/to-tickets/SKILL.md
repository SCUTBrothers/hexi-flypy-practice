# 拆解垂直切片任务单（to-tickets）

读取已定稿的 `spec.md` 与当前仓库相关代码，将中大型改动拆解为一组顺序推进、可独立验证的垂直切片任务单。本技能只产出任务单并停下等待审阅，不修改业务代码。

## 前置核查

- 先完整读取目标 `spec.md`（若引用了上游需求文档，按需核对关键细节）并快速核实当前仓库相关目录结构。
- 若尚未形成定稿的 `spec.md`，或其中仍有阻塞性未决分歧，先用 `to-spec` 冻结共识再切片。
- 若任务体量很小（单个短会话即可完整实现并验证），直接说明无需切片，避免无谓拆单。

## 切片原则

1. **垂直切片（Tracer Bullets）**：遵循 `principle-sequence-verifiable-units`，每个切片必须打穿端到端所需的最小路径并可独立验证；严禁按代码层横切（例如把“写全部类型 → 写全部接口 → 写全部页面”拆成彼此无法单独验收的碎片）。
2. **单上下文窗口粒度**：每个切片须足够收敛，使一个全新空白会话只读 `spec.md` 与当前切片文件就能独立完成实现、验证与提交。中大型需求通常拆为 3–7 片。
3. **显式依赖边**：仅声明真实前置依赖；无直接依赖的切片保持平行，方便某一片受外部阻塞时先推进另一片。
4. **增量追加，不改写已完成历史**：当已有 `tickets/` 目录且后期新增需求或优化意见时，绝不改写已标 `status: done` 的旧切片；沿最大编号顺延追加新文件（如 `06-ui-polish.md`），并在 `depends_on` 中声明依赖。

## 单切片标准格式

- 文件命名：`01-<kebab-slug>.md`、`02-<kebab-slug>.md`……按建议执行顺序两位数字编号。
- 顶层固定 4 字段合法 YAML frontmatter：

```yaml
---
type: ticket
status: todo
depends_on: []
commit: ''
---
```

- `status` 仅取 `todo`、`in-progress`、`blocked` 或 `done`。
- `depends_on` 填前置切片的文件名去扩展名（例如 `01-list-and-permissions`）。
- `commit` 初始留空字符串，待 `run-ticket` 完成后回填提交短哈希。

- 正文固定四个紧凑小节：
  1. **目标（Why & What）**：用 1–3 句话交代本片交付的可见行为与存在理由。
  2. **关键约定**：本片需遵守的模块边界、复用对象、数据/接口约束（不写逐行伪代码）。
  3. **不碰范围（Out of Scope）**：明确禁止顺手改动的其他切片、公用模块或重构项。
  4. **验收标准（Verification）**：可实际运行的命令、测试用例或交互核验断言，确保完成后能客观判绿。

## 读写载体与落盘位置

- **外部载体优先**：若当前指令、项目 `AGENTS.md` 或注入规则指定了非本地载体（例如通过 `gh` CLI 创建 GitHub Issues），严格遵循该约定；**向远端平台批量创建 Issue 前，必须先在对话中列出完整切片标题、依赖图与核心内容预览，经用户明确批准后再执行创建**。
- **默认本地 Markdown 目录**：按以下顺序确定 `tickets/` 落盘目录：
  1. 用户在当前消息中显式指定的目录；
  2. 所读 `spec.md` 的同级目录 `tickets/`；
  3. 项目 `AGENTS.md` 或注入规则声明的存放约定；以上均未指定时，先向用户确认目录再写入。

## 交付与审阅门禁

落盘后在对话中输出一张简明总览表（编号、目标、依赖、验收入口），停下请用户审阅确认。审阅通过后，引导用户在新会话中按顺序调用 `run-ticket` 逐片执行。
