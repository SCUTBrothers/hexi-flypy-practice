# 改动中的代码坏味道

将以下十二项作为审查线索，而不是机械扣分清单。核查时回到具体调用方，确认改动让谁多背了不必要的内部知识、被迫同步多处修改或引入出错风险，再给出最小调整建议。若仅是代码外形相似或个人风格偏好，无需强行挑刺，零发现完全合理。

| 坏味道线索                                     | 核实方式与处理思路                                                                            |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 命名含糊（Mysterious Name）                    | 仅看调用处能否明白名称对应的值或行为？如果换个名字依然说不清含义，检查是否混入了两种职责。    |
| 重复代码（Duplicated Code）                    | 找出重复位置并取一个真实调用核对：若业务规则、默认值和副作用完全一致，改为复用已有实现。      |
| 行为错位（Feature Envy）                       | 一段逻辑是否反复读取另一模块的内部状态？评估能否由掌握该状态的模块直接暴露所需结果。          |
| 成组数据（Data Clumps）                        | 同一批字段是否在多个入口总是一起传递并共同受约束？具备稳定业务含义时再收敛为一个值对象。      |
| 原始类型承载领域概念（Primitive Obsession）    | 两个含义不同的字符串或数值是否容易传错混用？考虑复用已有领域类型，并在输入边界完成校验。      |
| 重复分支（Repeated Switches）                  | 同一种业务分类在多处分别 `switch` / `if` 判断，新增一项要同步几处？将共同决策收拢到同一映射。 |
| 一处规则牵动多处修改（Shotgun Surgery）        | 顺着本次规则变更列出所有被迫联改的文件，判断散落的业务知识能否收归同一模块。                  |
| 一个模块因多种原因变化（Divergent Change）     | 识别模块内彼此独立的演进动因，按职责拆开，同时保持调用方所需的接口稳定。                      |
| 为假想需求过度通用化（Speculative Generality） | 新增的参数、配置、钩子或包装层有哪个真实调用方在用？可直接删掉的标出具体位置。                |
| 消息链（Message Chains）                       | 调用方是否需要层层穿透别人的内部结构？改由掌握内部结构的模块直接提供高层操作。                |
| 中转层（Middle Man）                           | 删掉这层转发后，默认值、校验、错误处理与副作用是否依然成立？成立则直接调用底层入口。          |
| 不合适的继承（Refused Bequest）                | 子类或实现是否忽略了父契约的大部分能力，导致按父类型调用时表现意外？考虑收缩契约或改用组合。  |
