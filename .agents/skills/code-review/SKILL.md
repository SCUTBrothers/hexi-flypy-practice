# 评审当前改动（code-review）

以只读方式审查改动，并在当前会话中交付可操作的结论。

## 1. 锁定需求、范围与规范

- **确认最终需求**：从本轮用户最终确认的要求中提取预期行为、明确排除的事项，以及现有调用方必须保持的行为。需求存在空白时，顺着用户提供的文档、PR、提交关联工单或匹配的本地规格说明查证；若旧说明与本轮决定冲突，明确点出差异。仍缺依据的条目记为未核对，继续审查已有契约。
- **锁定审查范围**：优先采用用户指定的补丁、文件、暂存区、提交或 PR。审查分支或 PR 时，先校验基准引用可解析、确认纳入范围的提交，再对比合并基点与待审提交；仅审暂存区时，严格读取并验证暂存快照；审工作区时，涵盖已暂存、未暂存及相关未跟踪文件。当用户说「审这次改动」时，一并覆盖本轮相关提交与工作区剩余改动，并写明实际采用的范围。基准存在歧义且影响结论时先向用户澄清；指定范围为空则直接说明。
- **区分需求与规范**：分别核对业务需求与仓库规范。先查阅适用于改动目录的项目指引、`CONTRIBUTING.md`、`CODING_STANDARDS.md` 及其指向的文档，同时检索与本次契约直接相关的独立说明。需求偏差指出原要求，规范违规引用具体文件、条款与违规改动。已由 lint 或类型检查覆盖的规则以工具输出为准，同一问题不重复报告。

## 2. 沿真实调用路径核实

1. **逐项追踪行为契约**：从输入沿调用链路追踪至输出与持久化写入点，核查漏做、部分实现、实现有误与越界行为。通读被改函数的调用方、被调函数及已有测试；凡签名、返回值、报错方式或行为契约发生变化，必须全局检索所有调用方。对于可能各自独立出错的行为，分别选用能暴露对错的输入逐一核实（例如零金额与跨日归属可能在同一笔交易上分别出问题，须分开检验）。
2. **优先排查正确性与安全边界**：检查外部输入在何处校验、敏感数据流向何方，以及发生部分写入、异常失败或重试后系统状态是否保持一致。优先运行安全且聚焦的现有检查，并用真实调用举例说明。
3. **结合实际负载评估风险**：从 README、部署配置或运行入口确认预期的数据量、进程数与并发模型，据此判断「先查后写」、跨进程重复执行、无界增长、N+1 查询或冗余计算会引发什么后果。对于本轮已明确接受且仍满足契约的限制，只有实际使用条件越过该限制时才列为问题；明确区分会拖慢真实负载的瓶颈与微不足道的细枝末节，负载条件未知时标明判断前提。针对关键分支、数据解析、金额计算、安全、持久化与回归修复，指出哪种错误本应让哪个入口的测试失败。
4. **审视可删减项与坏味道**：在满足需求的前提下，核对有哪些死代码、无用配置项、平台原生已有能力或多余依赖可以去掉。建议复用时给出已有实现的位置，并核对默认值、错误处理与副作用是否一致；建议拆分时写清各自独立的职责（代码行数本身不足以成为拆分理由）。对照 [改动中的代码坏味道](./references/code-smells.md) 逐项检查，仓库明文允许的写法遵循仓库约定；报告坏味道时点名对应线索、具体代码位置与实际维护代价。

## 3. 输出清晰结论

开篇用一句话概括本次改动的实际行为。随后按严重程度从高到低连续编号（方便用户按编号挑拣处理）：先列阻塞合并的问题，再列有据可依的改进项与可选精简建议。每条发现须包含**文件与行号、判断依据、触发场景、实际后果与最小修正方向**；同一根因合并成一条，同时保留关联的需求与规范依据。

结尾交代哪些项应优先修复、实际运行了哪些检查，以及还有哪些重要条件尚未核实。若无问题，说明审查范围与核验依据即可。
