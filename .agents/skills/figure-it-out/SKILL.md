# 量身设计任务执行流程（figure-it-out）

当手头任务无法套用任何现成的操作流程（playbook）时，就亲手设计一套。在写下任何一行代码之前，你的首个交付物就是**工作流本身**：一套与任务风险相匹配的分阶段流程，遵循科学实验方法推进，并留下一条完整清晰、供人类离开归来后随时审计的决策轨迹。

## 启动准备

首先创建待办清单（todolist），将下方各个阶段依次加入待办清单。

## A 阶段：界定问题框架（Frame）

先摸清底细，再投入执行。在能够明确陈述以下三点之前，绝不盲目启动任务：

- **可证伪的完成定义（Definition of Done）**：将其表述为一个可明确判定真假的谓词条件（遵循 `principle-prove-it-works` 原则技能）。
- **量化的任务范围**：估算大致的任务单元数量与工作量，并列出前期摸底暴露出的阻塞项（blockers）。
- **宁高勿低的严谨度档位**：面对不可逆的“单向门（one-way doors）”决策或波及范围广的高风险改动，必须拉满严谨度；面对可逆的低风险步骤，则可适当从简。注意：所谓“严谨”，体现在实打实的准入检查（gates）与验证产物上，而不是喊一句“更努力一点”的口号。

在正式投入长时间运行之前，先向用户呈现问题框架与利弊权衡。虽然可逆的工作应直接推进（遵循 `principle-never-block-on-the-human` 原则技能），但长达数小时的大规模运行值得在启动前设一个人工确认检查点。

## B 阶段：设计工作流（Design the workflow）

将总体目标拆解为原子化、可独立合入的最小工作单元，并按“最大未知风险优先（riskiest-unknown-first）”的顺序编排。验证脚手架与基础结构必须排在业务功能开发之前（遵循 `principle-foundational-thinking` 原则技能）。

- 在动手改业务代码前先搭建验证脚手架（verification harness），并从改动前的基线状态采集基准数据，使后续每一次检查都能直观呈现为“旧值 vs 新值”的对比。
- 遇到不可逆的“单向门”架构决策时，运行 `architect` 技能（它会按需转交 `arena`）；对于目标形态已经非常明确的机械性修改，则直接跳过。对已经敲定的设计再跑一轮 `arena` 纯属过度设计（遵循 `principle-laziness-protocol` 原则技能）。
- 决定哪些环节可以并行分发（fan out）。只在模块边界（seams）清晰的地方并行化，并为每个工作子智能体分配独立的 Git 工作树或分支（遵循 `principle-separate-before-serializing-shared-state` 原则技能），切忌盲目过度分发。
- 将设计好的阶段清单明确写下来——这份清单正是人类审阅者要看的核心蓝图。

随后执行这套设计：将拆解出的具体步骤作为待办项插入到待办清单的 C 阶段与 D 阶段之间，在 C 阶段的实验循环纪律下逐一推进，并在每一步落地时实时追加一行 D 阶段决策日志，切勿等到全部跑完最后再一次性补写整条轨迹。

## C 阶段：运行实验循环（Run the loop）

每个工作单元都是一次受控实验：明确陈述假设 → 做出最小改动 → 在真实产物上对照判定谓词进行测量 → 若指标改善则保留，若未改善则立即回滚。遵循 `principle-sequence-verifiable-units` 原则技能，每个单元都必须先完成验证再启动下一个单元，绝不把验证攒到最后批量跑。

- 必须通过直接检查真实产物来验证，绝不采信智能体的自我口头汇报。当某项检查赢得过于轻松时，先怀疑观测手段本身是否有漏洞，再看被测系统。
- 为委派出去的任务配一名独立评审子智能体（judge）。若发现工作子智能体钻准入检查的空子（gaming the gate），立即重置并收紧契约；若发现准入检查本身写错了，单独提交一笔改动修复准入检查，绝不绕过检查强推。
- 验收结论只有三种：`VERIFIED`（已验证）、`NOT VERIFIED`（未验证）或 `INCONCLUSIVE`（结论不明确）。“结论不明确”绝不等于通过，切勿掩盖任何负面结果。

## D 阶段：留存审计轨迹（Keep the audit trail）

通过 `show-me-your-work` 技能全程记录运行过程。用到 `figure-it-out` 的任务通常规模庞大，值得将决策轨迹文件一并提交到分支中，方便审阅者直接在 PR 里对照阅读。“决策轨迹 + 代码 diff”是让人类离开归来后依然能够充分信任交付成果的关键。

## E 阶段：整体终验与交接（Verify and hand back）

脱离局部测试脚手架，直接在真实产品上对照 A 阶段立下的完成谓词做一次端到端整体终验。将执行过程中反复出现的纠偏经验固化为准入检查、lint 规则、自动化校验或脚本（遵循 `principle-encode-lessons-in-structure` 原则技能）。

**回复：** 你设计的操作流程、选定的严谨度档位及原因、决策轨迹文件路径、对照完成谓词已验证通过的内容，以及仍未解决的遗留事项。
