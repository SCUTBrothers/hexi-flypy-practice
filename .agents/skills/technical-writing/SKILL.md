# 技术写作（technical-writing）

写出来的文字要让疲惫的工程师第一遍就能看懂。默认面向中文技术写作，同时兼容中英混排与全英文文档（如英文仓库文档、RFC、PR 与提交信息）。

- 删掉所有不起作用的词。
- 用简短朴素的日常词：写“用”而非“进行利用 / 加以运用”，写“改”而非“进行修改”（英文写 `"use"` 而非 `"utilize"`）。
- 如果生套某条规则反而让句子别扭，就换个顺畅写法，或者干脆不动。
- 直接写真实的符号、文件、参数标志或命令名，不要换用同义词或绕弯子描述。
- 不要生造行话。用开发者平时会脱口而出的词；首次引入非通用的命名模式或概念时，当场用一句话说清含义。

## 错落有致的节奏

- 长短句交错使用。把硬塞了两层意思的句子拆开；把只顺畅表达一层意思的长句留住。
- 原理解析（Explanation）要亮明判断与取舍；参考手册（Reference）保持平实克制。
- 表达务必具体。不要写“表结构变更可能引发问题”（`"schema changes can cause issues"`），要写“重命名列会导致构建失败”（`"a column rename fails the build"`）。

## 先选定文档模式（Diátaxis）

一篇文档只用一种模式。切勿把多种模式揉在同一篇里，应拆开并互相链接。

- **教程（Tutorial）：边做边学。** 开篇写明读者完成后将构建出什么。每一步都产出可见结果，并明确说明此时应该看到什么现象。原理解释最多只占半句外加一个链接。
- **操作指南（How-to）：达成目标的步骤。** 解决读者的具体实际问题。默认读者具备基础能力。只写操作动作，允许按实际条件分出分支路径。直接用具体任务为指南命名（如“如何轮换数据库密钥”）。
- **参考手册（Reference）：供查阅的事实。** 只做客观描述。行文平实、完整、确凿。文档结构与被描述代码或接口自身的结构保持一致。
- **原理解析（Explanation）：阐明理解与“为什么”。** 聚焦单一且边界清晰的主题。交代设计背景：取舍依据、演进历史、约束条件与淘汰过的备选方案。只有在此模式下才允许展开观点争鸣，其他模式一律禁止。

## 面向读者写句子（Google 开发者风格）

- 用第二人称“你”（英文用 `you`）和现在时直接对话，少写疏离的“用户应当……”。
- 点明谁做了什么。清理中文里泛滥的“被、受到、加以、进行、予以”式空泛被动（如把“配置会在启动时被加载并进行校验”改为“服务在启动时加载并校验配置”）；只有当执行主体未知或确实无关紧要时才用被动语态。
- 操作指令写成直接的祈使句。前提条件放在操作指令之前，最常见的主路径放在最前面。
- 不用互联网黑话，不用比喻修辞，不用客套冗余的“请务必”（英文不用 `"please"`）；操作步骤中绝不用“只需简单地”“轻松”“快速”（英文不用 `"simply"`、`"easy"`、`"quickly"`）。
- 不写“接下来本文将介绍……”式的预告铺垫，也不让相邻句子用相同的句式开头。
- 链接文本直接写明跳转目标（如“参见配置项参考”），不写“点击这里”“详见此处”。
- 标题直奔要点，不堆砌书名号或口号；英文标题采用句首字母大写（Sentence case）。每页只有一个一级标题（`h1`），禁止跳级使用标题。
- 有先后顺序的操作步骤用有序列表，其余一律用无序列表。用完整的句子引出列表，各列表项保持句式结构平行。
- 代码、命令、路径与配置键使用等宽代码体（`` `code` ``），界面元素使用**粗体**。删掉笼统兜底的“等 / 等等”（英文删掉 `"etc."`，并列项使用牛津逗号）。

## 让读者一次只接收一层意思（STE 受控写作规则）

- 操作指令每句只写一步动作；其余正文每句只表达一层意思。
- 控制单句长度：中文操作指令超过约 35 字、普通句子超过约 50 字时拆短（英文分别控制在约 20 词、25 词以内），避免多层“的”字长定语缠绕。
- 把警告或前置条件放在所保护的操作步骤之前，切勿等读者执行完才在句末补一句“注意：这会清空数据”。
- 一词一义：同一个概念或动作在全文固定使用同一个词，不要在同一段里把“工作区 / 目录 / 文件夹”或“调用 / 触发 / 唤起”轮换着用。
- 操作规程一律写成直接动作，不用旁白叙述，不用“通过……方式来进行……操作”式的公文腔（英文尽量少用 `-ing` 动名词堆砌，并保留冠词 `"the"` / `"a"` 以防歧义）。

## 不给句子留出歧义空间（精准表达与中英混排）

- 把“只 / 仅”“不 / 未”（英文 `"only"`、`"not"`）等限定词紧挨着它所修饰的词放置。
- 拆开连串的名词堆叠（如把“异步任务状态持久化重试队列配置”拆成“配置异步任务队列的状态持久化与重试策略”）。
- 消除模糊指代：让每个“它 / 这 / 该”（英文 `"it"` / `"they"` / `"this"`）都指向唯一明确的对象，绝不用“这”或 `"this"` / `"which"` 笼统指代前面整句话。
- 不写缺主语、纯靠箭头拼凑的电报式残句（如将“解析器遇到非法日期 → 退出码 2”写完整为“解析器拒绝非法日期，以退出码 2 退出且不写入文件”；英文同样不省略动词或标示句法结构的 `"that"`）。
- 列举并列条件时写清“且（`and`）”与“或（`or`）”的作用边界，不用斜杠 `/` 充当含糊连词（如“请求/响应校验”应写清是“校验请求与响应”还是二选一），英文不用 `"(s)"`。
- 用逗号和句号自然断句，少用分号，不用破折号串联半截话；括号内的补充说明自身必须构成完整的语法单位。
- **自然处理中英混排**：优先使用地道顺畅的中文；行业通用缩写（如 `API`、`SQL`、`HTTP`、`AST`）、真实代码标识符，以及尚无贴切中文译法或英文原词在工程语境下更精准的概念可直接保留英文，但不要夹杂 `leverage`、`align`、`deliver`、`insight`、`case`、`review` 等完全可用朴素中文替代的职场装腔词。中英文之间保持清晰视觉边界，不在中文句子里硬套英文从句语序。

## 文风与仓库规范

- 结合 `unslop` 技能去除 AI 写作套话、空泛大词、翻译腔与模棱两可表述（技术文档保留必要的标题层级、步骤列表与标准技术标点，不套用叙事评论文章的口语俚语要求）。
- PR 描述和提交信息同样属于技术写作，除 Diátaxis 之外的所有层级规范均适用。撰写 PR 正文时按 `pr` 组织行为变化、验证依据与合并风险，长日志改为贴链接。
- 产品 UI 界面文案不属于技术文档，遵循产品自身的界面文案规范。
- 代码片段缩进与目标仓库保持一致，路径写真实路径。凡提及数量统计或目录树结构，必须保证在合入提交那一刻完全属实，并附上重新生成该数据的命令。
